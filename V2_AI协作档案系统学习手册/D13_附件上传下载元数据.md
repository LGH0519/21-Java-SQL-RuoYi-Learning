# Day 13：附件上传、下载与元数据

## 知识速记

附件功能分两部分：文件本体由现有上传能力保存到受控文件位置；附件元数据由 `archive_attachment` 表保存并关联档案。页面不能直接相信文件名或路径；后端必须校验关联档案、权限、空文件和允许类型/大小。

## 资料

- 本机 `CommonController` 中上传/下载相关方法（只读）。
- `application.yml` 的 `ruoyi.profile` 和 multipart 配置（只读，绝不公开路径/凭据）。
- D10 的 `archive_attachment` 表。

## 知识详解

文件本体不是数据库字段；元数据至少有档案 ID、原文件名、存储名/相对路径、大小、类型、上传人、上传时间。上传成功不等于业务完成：还需要写元数据；下载需要根据附件 ID 找元数据并做权限验证。第一版只存非敏感测试文件，不做在线预览和版本控制。

## 今天照做（09:00–23:00）

### 09:00–12:00

1. 只读找到若依现有上传/下载接口，记录 URL、输入、返回的关键字段；不复制真实文件路径。
2. 画流程：选择文件 → 上传接口 → 返回保存信息 → 新增附件元数据 → 档案详情列表 → 下载接口。
3. 为附件表补齐字段字典与权限：上传、下载、删除分别谁可做。

### 15:00–18:00

1. 用生成器或 AI 生成附件元数据基础 CRUD；AI 先给文件清单和校验策略。
2. 使用一个虚构 `.txt` 或小图片测试上传；用 Network 记录上传响应，遮挡路径/token。
3. 将上传响应必要字段保存为关联当前档案的附件元数据；DBeaver 核对一条记录。
4. 从档案详情/附件列表下载该文件，核对文件名与大小。

### 19:00–23:00

1. 测空文件/未选文件、无档案关联、未知附件 ID、权限不足四种失败情形；只在测试数据上操作。
2. 让 AI 审查“上传成功但元数据插入失败”的风险，要求它提出补偿/事务方案，记录为后续改进；不要凭空实现复杂分布式事务。
3. Debug 元数据保存的 Controller/Service，记录输入的 archiveId 与文件返回字段。

## 文末答案与自测

**为什么附件要分本体和元数据？** 文件存储方式与业务查询/权限记录不同，分开更可维护。  
**通过标准：** 能解释上传后还必须保存什么、下载前还必须验证什么。
