# 报名系统独立开发知识地图

## 一、先理解整个项目

### 1. 浏览器、前端、后端、数据库

一个完整请求的流程：

```
浏览器
  ↓
Vue前端页面
  ↓ HTTP请求
Spring Boot后端
  ↓
Service业务层
  ↓
Mapper数据访问层
  ↓
MySQL数据库
```

返回时方向相反：

```
MySQL
  ↓
Mapper
  ↓
Service
  ↓
Controller
  ↓ JSON
Vue页面
```

需要理解：

- 前端负责显示页面、收集输入；
- 后端负责权限、业务规则、数据校验；
- 数据库负责持久化保存数据；
- 前端不能替代后端权限校验；
- 数据库不能替代全部业务逻辑。

## 4. Vue 3

### 4.1 单文件组件

Vue页面通常由三部分组成：

```
<template>
  页面结构
</template>

<script setup>
  页面逻辑
</script>

<style scoped>
  页面样式
</style>
```

分别对应：

- `template`：显示什么；
- `script`：数据和操作；
- `style`：如何显示。

---

### 4.2 `ref`

`ref`用于定义响应式数据。

```
const count = ref(0)
```

修改：

```
count.value = 1
```

模板中使用：

```
<span>{{ count }}</span>
```

在模板中通常不需要写 `.value`。

---

### 4.3 `reactive`

`reactive`也用于响应式对象。

```
const form = reactive({
  realName: "",
  phoneNumber: ""
})
```

与`ref`的区别：

- `ref`适合基本类型或整体替换对象；
- `reactive`适合直接操作对象属性；
- 项目中要遵循已有代码风格，不要随意混用。

---

### 4.4 `computed`

`computed`用于根据已有数据计算新数据。

```
const isEditable = computed(() => {
  return ["0", "3", "4"].includes(
    form.value.status
  )
})
```

含义：

```
状态是0、3、4 → 可以编辑
状态是1、2 → 不可以编辑
```

它与普通变量不同：

```
const a = form.value.status === "0"
```

普通变量只计算一次，而`computed`会随着依赖的数据变化自动更新。

---

### 4.5 `watch`

`watch`用于监听数据变化。

```
watch(
  () => route.params.registrationId,
  registrationId => {
    loadDetail(registrationId)
  }
)
```

作用：

- 监听路由中的报名ID；
- ID变化时重新查询详情；
- 常用于路由切换、筛选条件变化、联动查询。

---

### 4.6 生命周期

常见生命周期：

```
onMounted(() => {
  loadCurrentRegistration()
})
```

表示页面加载完成后执行查询。

常见用途：

- 初始化页面；
- 查询后端数据；
- 加载字典；
- 获取当前用户信息。

---

### 4.7 模板指令

#### `v-model`

实现双向绑定：

```
<el-input v-model="form.realName" />
```

用户输入时：

```
输入框内容 → form.realName
```

程序修改时：

```
form.realName → 输入框显示内容
```

#### `v-if`

条件显示：

```
<div v-if="form.status === '1'">
  待审核
</div>
```

#### `v-for`

循环显示：

```
<el-option
  v-for="item in registration_position"
  :key="item.value"
  :label="item.label"
  :value="item.value"
/>
```

#### `:disabled`

动态设置是否禁用：

```
:disabled="!isEditable"
```

#### `@click`

监听点击事件：

```
@click="handleSubmitRegistration"
```

#### `v-hasPermi`

若依权限指令：

```
v-hasPermi="['registration:personal:submit']"
```

它只能控制前端按钮是否显示，真正的权限仍然必须由后端检查。

常见注解：

```

```


```
@Autowired
```

## 3. Controller层

Controller接收前端请求。

```
@PostMapping("/submit")
public AjaxResult submitRegistration()
{
    Long userId = getUserId();

    return toAjax(
        service.submitRegistration(...)
    );
}
```

Controller主要做：

- 接收请求；
- 获取登录用户；
- 获取参数；
- 调用Service；
- 返回结果。

Controller不应该承担大量业务判断。

---

## 4. Service层

Service负责业务规则。

例如：

```
if (!"1".equals(registration.getStatus()))
{
    throw new ServiceException(
        "只有待审核状态可以撤回"
    );
}
```

这就是业务规则。

Service常见工作：

- 判断数据是否存在；
- 判断状态是否正确；
- 校验业务条件；
- 组装对象；
- 调用Mapper；
- 处理事务；
- 处理业务异常。

---

## 5. Service接口和实现类

接口：

```
public interface IBizRegistrationService
{
    public int submitRegistration(...);
}
```

实现类：

```
@Service
public class BizRegistrationServiceImpl
        implements IBizRegistrationService
{
    @Override
    public int submitRegistration(...)
    {
        // 业务实现
    }
}
```

接口的作用：

- 定义业务能力；
- Controller依赖接口；
- 隐藏具体实现；
- 方便后续替换实现或测试。

---

## 6. Mapper层

Mapper负责调用数据库。

```
public int updateRegistrationToSubmitted(

```

Mapper接口本身通常只声明方法，真正SQL写在XML中。

## 8. Java对象和数据库字段映射

# 四、数据库知识

## 1. 表、字段、记录

例如：

```
biz_registration
```

是一张表。

```
real_name
phone_number
status
```

是字段。

一名用户的一条报名信息是记录。

---

## 2. 主键

```
registration_id bigint primary key auto_increment
```

作用：

- 唯一标识一条报名记录；
- 不能重复；
- 通常使用自增ID。

---

## 3. 外键关系

报名表中：

```
user_id
```

表示这条报名属于哪个系统用户。

逻辑关系：

```
sys_user 1 ─── N biz_registration
```

意思是：

- 一个系统用户可以有多条报名记录；
- 每条报名记录属于一个用户。

即使数据库不设置物理外键，也必须在业务和SQL中保证关系正确。

---

## 4. 唯一约束

报名业务要求：

```
同一个用户同一年只能报名一次
```

可以使用唯一索引：

```
unique key uk_user_year (user_id, registration_year)
```

这是数据库层面的最后保障。

不能只依赖Java判断，因为并发请求可能同时通过Java判断。

---

## 5. `not null`和默认值

```
status char(1) not null default '0'
```

表示：

- 状态不能为空；
- 新建记录时默认是草稿。

不是所有字段都应该`not null`。

例如：

- 报名状态：应该非空；
- 用户ID：应该非空；
- 报考职位：草稿阶段可以为空；
- 审核时间：未审核时应该为空；
- 审核意见：未审核时应该为空。

---

## 6. 逻辑删除

若依常使用：

```
del_flag
```

例如：

```
0：正常
2：删除
```

SQL查询要注意：

```
and del_flag = '0'
```

否则可能查询出逻辑删除的数据。

---

## 7. 索引

索引用于提高查询速度。

报名表常见查询：

```
where user_id = ?
  and registration_year = ?
```

因此适合建立：

```
index idx_user_year (
    user_id,
    registration_year
)
```

索引不是越多越好，因为：

- 会占用空间；
- 会降低新增和修改速度；
- 查询字段变化后可能失效。

---

## 8. 事务

事务保证一组操作要么全部成功，要么全部失败。

例如提交报名可能包括：

```
保存草稿
修改状态为待审核
清空旧审核信息
```

如果这些操作被拆开，就可能出现部分成功。

需要学习：

- `@Transactional`;
- 提交；
- 回滚；
- 事务边界；
- 事务失效的常见原因。

---

# 五、报名系统业务知识

## 1. 状态机

当前状态：

```
0：草稿
1：待审核
2：审核通过
3：审核不通过
4：已撤回
```

状态流转：

```
草稿 → 待审核
待审核 → 审核通过
待审核 → 审核不通过
待审核 → 已撤回
审核不通过 → 待审核
已撤回 → 待审核
```

不能随便允许状态跳转，例如：

```
审核通过 → 已撤回
```

通常应该禁止。

---

## 2. 前端状态和后端状态

前端：

```
:disabled="!isEditable"
```

只是改善页面体验。

后端仍然必须判断：

```
if (!"1".equals(registration.getStatus()))
{
    throw new ServiceException(...);
}
```

真正的安全规则必须在后端。

---

## 3. 权限和角色

若依权限结构：

```
用户
  ↓
角色
  ↓
菜单和按钮权限
```

例如：

```
registration:personal:query
registration:personal:save
registration:personal:submit
registration:personal:withdraw
registration:manage:list
registration:manage:query
registration:manage:audit
```

前端权限：

```
v-hasPermi="['registration:personal:submit']"
```

后端权限：

```
@PreAuthorize(
    "@ss.hasPermi('registration:personal:submit')"
)
```

两边都要控制。

---

## 4. 当前用户和管理员

报名人员接口不能接收前端传来的任意`userId`。

正确做法：

```
Long userId = getUserId();
```

管理员查询可以查看多名报名人员，但仍然需要权限：

```
@PreAuthorize(
    "@ss.hasPermi('registration:manage:list')"
)
```

# 六、附件模块需要掌握的知识

## 1. 文件上传流程

```
选择文件
  ↓
前端上传请求
  ↓
后端接收MultipartFile
  ↓
保存文件到磁盘或对象存储
  ↓
数据库保存文件信息
  ↓
返回文件地址
```

---

## 2. 附件表设计

不建议在报名主表中增加很多文件字段。

建议：

```
biz_registration_attachment
```

至少包含：

```
attachment_id
registration_id
attachment_type
original_name
file_name
file_url
file_size
content_type
create_by
create_time
```

这样可以支持：

```
身份材料
学历证明
学位证明
其他材料
```

---

## 3. 文件和数据库的区别

数据库通常保存：

```
文件名称
文件路径
文件类型
文件大小
上传人
关联报名ID
```

不建议第一阶段直接把大文件二进制放进数据库。

---

## 4. 上传安全

需要检查：

- 文件大小；
- 文件扩展名；
- MIME类型；
- 文件名；
- 是否允许脚本文件；
- 是否能越权下载；
- 是否只能操作自己的附件；
- 管理员是否可以查看附件。

# 最终学习目标

不是记住所有生成的代码，而是逐渐能够回答：

```
这个页面由哪个路由打开？
它调用哪个API？
API进入哪个Controller？
Controller调用哪个Service？
Service执行哪些业务判断？
Mapper执行哪条SQL？
SQL修改了哪些字段？
谁有权限调用？
异常时返回什么？
如何验证数据库真的成功？
```

当你能够独立回答这几个问题，并能从数据库、后端日志、浏览器Network三个位置定位问题时，才算真正开始具备独立开发能力。
