# 若依数据库全景图

把整个系统想象成一家**公司**：

```
部门表(sys_dept)     → 公司的组织架构图
用户表(sys_user)     → 员工花名册
岗位表(sys_post)     → 职位列表（董事长、经理...）
角色表(sys_role)     → 权限角色（管理员、普通员工...）
菜单表(sys_menu)     → 系统功能清单（能看到哪些页面、按钮）
关联表(3张)          → 谁拥有什么角色/菜单/岗位
字典表(2张)          → 翻译本（0=男, 1=女...）
参数表(sys_config)   → 系统设置（初始密码、皮肤...）
日志表(2张)          → 操作记录 + 登录记录
任务表(2张)          → 定时任务（自动执行的程序）
公告表(2张)          → 通知公告 + 已读记录
代码生成表(2张)      → 代码生成器的配置
```

---

## 表1：`sys_dept` 部门表

> **类比**：公司的组织架构图，像家谱一样有上下级关系。

```
若依科技 (dept_id=100, parent_id=0)
├── 深圳总公司 (101, parent_id=100)
│   ├── 研发部门 (103, parent_id=101)
│   ├── 市场部门 (104, parent_id=101)
│   └── 测试部门 (105, parent_id=101)
└── 长沙分公司 (102, parent_id=100)
    ├── 市场部门 (108, parent_id=102)
    └── 财务部门 (109, parent_id=102)
```

| 字段 | 含义 | 为什么需要 | 搭配作用 |
|------|------|-----------|---------|
| `dept_id` | 部门唯一编号 | 区分每个部门 | 主键，被 `sys_user.dept_id` 引用 |
| `parent_id` | 父部门编号 | 建立上下级关系 | 和 `ancestors` 搭配实现树形结构 |
| `ancestors` | 祖级列表 | 快速查询所有上级/下级 | 如 `0,100,101` 表示"若依科技→深圳总公司"，**不用递归查询**就能找到整条链路 |
| `dept_name` | 部门名称 | 显示用 | — |
| `order_num` | 显示顺序 | 控制部门在列表中的排列顺序 | — |
| `leader` | 负责人 | 知道这个部门谁管 | — |
| `phone` / `email` | 联系方式 | 联系部门负责人 | — |
| `status` | 状态 | 停用部门后，该部门下的用户不能登录 | 配合 `del_flag`：`status=1` 停用但数据还在，`del_flag=2` 彻底删除 |
| `del_flag` | 删除标志 | **逻辑删除**，数据不真正删 | 设为 `2` 后查询时自动过滤，但数据还在数据库里，可以恢复 |
| `create_by/create_time` | 创建者/时间 | 审计：谁什么时候建的这个部门 | — |
| `update_by/update_time` | 更新者/时间 | 审计：谁什么时候改的 | — |

**删除的影响**：
- `del_flag` 设为 `2` → 该部门"消失"了，但数据还在
- 如果该部门下有用户，用户查询时会看不到这个部门
- `ancestors` 机制让删除父部门时，可以快速找到并处理所有子部门

## 表2：`sys_user` 用户信息表

> **类比**：公司的员工花名册，记录每个人的基本信息。

| 字段 | 含义 | 为什么需要 | 搭配作用 |
|------|------|-----------|---------|
| `user_id` | 用户唯一编号 | 区分每个用户 | 主键，被多张表引用 |
| `dept_id` | 所属部门 | 知道用户在哪个部门 | 关联 `sys_dept.dept_id`，实现**数据权限**（本部门数据 vs 全部数据） |
| `user_name` | 登录账号 | 用户登录时输入的账号 | 唯一，用于登录认证 |
| `nick_name` | 昵称 | 页面上显示的友好名称 | 和 `user_name` 不同：`user_name=admin`，`nick_name=若依` |
| `user_type` | 用户类型 | 区分系统用户和外部用户 | `00`=系统用户，未来可扩展 |
| `email` / `phonenumber` | 邮箱/手机 | 联系方式，也可用于找回密码 | — |
| `sex` | 性别 | 基本信息 | 通过字典表翻译：`0`=男, `1`=女, `2`=未知 |
| `avatar` | 头像地址 | 页面显示头像 | 存的是图片URL |
| `password` | 密码 | 登录认证 | 存的是 **BCrypt 加密后的密文**，不是明文 |
| `status` | 账号状态 | 停用账号后用户无法登录 | `0`=正常, `1`=停用 |
| `del_flag` | 删除标志 | 逻辑删除 | `0`=存在, `2`=删除 |
| `login_ip` / `login_date` | 最后登录IP/时间 | 安全审计，知道用户最后一次在哪登录 | — |
| `pwd_update_date` | 密码最后更新时间 | 配合参数表的密码过期策略 | 如果超过设定天数没改密码，登录时提醒修改 |
| `create_by/create_time` | 创建者/时间 | 审计 | — |
| `update_by/update_time` | 更新者/时间 | 审计 | — |
| `remark` | 备注 | 额外说明 | — |

**删除的影响**：
- `del_flag=2` 后用户"消失"，无法登录
- 但关联表（`sys_user_role`、`sys_user_post`）中的数据不会自动清理
- 如果物理删除（`DELETE FROM`），外键关联的数据可能出问题

## 表3：`sys_post` 岗位信息表

> **类比**：公司的职位列表，如"董事长"、"项目经理"、"普通员工"。

| 字段 | 含义 | 为什么需要 |
|------|------|-----------|
| `post_id` | 岗位编号 | 主键 |
| `post_code` | 岗位编码 | 程序内部用的标识，如 `ceo`、`hr` |
| `post_name` | 岗位名称 | 页面显示的名称 |
| `post_sort` | 显示顺序 | 控制岗位在列表中的排列 |
| `status` | 状态 | 停用的岗位不能分配给用户 |

**和 `sys_user` 的关系**：通过 `sys_user_post` 关联表连接，一个用户可以有多个岗位。

## 表4：`sys_role` 角色信息表

> **类比**：公司的"权限角色"，比如"超级管理员"能看到所有功能，"普通员工"只能看到部分功能。

| 字段 | 含义 | 为什么需要 | 搭配作用 |
|------|------|-----------|---------|
| `role_id` | 角色编号 | 主键 | — |
| `role_name` | 角色名称 | 显示用，如"超级管理员" | — |
| `role_key` | 权限字符串 | 程序内部用的标识 | 后端代码中用 `@PreAuthorize("@ss.hasRole('admin')")` 判断 |
| `role_sort` | 显示顺序 | 排列用 | — |
| `data_scope` | 数据范围 | **核心字段**：控制这个角色的用户能看到哪些数据 | 见下方详细说明 |
| `menu_check_strictly` | 菜单树联动 | 勾选父菜单时是否自动勾选子菜单 | `1`=联动, `0`=不联动 |
| `dept_check_strictly` | 部门树联动 | 勾选父部门时是否自动勾选子部门 | 同上 |
| `status` | 状态 | 停用的角色不生效 | — |
| `del_flag` | 删除标志 | 逻辑删除 | — |

### `data_scope` 数据范围详解

这是若依最核心的权限设计之一，**决定了一个角色的用户能看到多少数据**：

| 值 | 含义 | 举例 |
|----|------|------|
| `1` | 全部数据权限 | 超级管理员能看到所有人的数据 |
| `2` | 自定义数据权限 | 手动指定能看到哪些部门的数据 |
| `3` | 本部门数据权限 | 只能看到自己部门的数据 |
| `4` | 本部门及以下 | 能看到自己部门和子部门的数据 |
| `5` | 仅本人数据 | 只能看到自己创建的数据 |

**搭配 `sys_role_dept` 表**：当 `data_scope=2` 时，通过 `sys_role_dept` 表指定这个角色能访问哪些部门的数据。

## 表5：`sys_menu` 菜单权限表

> **类比**：系统的"功能清单"，定义了所有页面和按钮，以及谁能用。

| 字段 | 含义 | 为什么需要 | 搭配作用 |
|------|------|-----------|---------|
| `menu_id` | 菜单编号 | 主键 | — |
| `menu_name` | 菜单名称 | 显示用 | — |
| `parent_id` | 父菜单编号 | 建立层级关系 | `0`=顶级，其他值=某个菜单的子项 |
| `order_num` | 显示顺序 | 控制排列 | — |
| `path` | 路由地址 | 前端路由路径 | 如 `user` 对应前端路由 `/system/user` |
| `component` | 组件路径 | 前端 Vue 文件位置 | 如 `system/user/index` 对应 `src/views/system/user/index.vue` |
| `query` | 路由参数 | 传递额外参数 | 一般不用 |
| `route_name` | 路由名称 | 前端路由的 name 属性 | 用于编程式导航 |
| `is_frame` | 是否外链 | `0`=外链（打开新网页），`1`=内链 | 如"若依官网"就是外链 |
| `is_cache` | 是否缓存 | `0`=缓存（切换页面不刷新），`1`=不缓存 | 提升用户体验 |
| `menu_type` | 菜单类型 | **核心字段** | `M`=目录（可展开的分组），`C`=菜单（可点击的页面），`F`=按钮（页面上的操作按钮） |
| `visible` | 是否显示 | `0`=显示在侧边栏，`1`=隐藏 | 隐藏的菜单存在但不显示 |
| `status` | 状态 | `0`=正常，`1`=停用 | 停用的菜单不显示 |
| `perms` | 权限标识 | **核心字段**：后端鉴权用 | 如 `system:user:add`，配合 `@PreAuthorize("@ss.hasPermi('system:user:add')")` |
| `icon` | 图标 | 侧边栏显示的图标 | — |

### 三层菜单结构

```
M 系统管理 (menu_id=1, parent_id=0)          ← 目录，可展开
  ├── C 用户管理 (100, parent_id=1)          ← 菜单，点击加载页面
  │     ├── F 用户查询 (1000, parent_id=100) ← 按钮，控制"查询"按钮是否显示
  │     ├── F 用户新增 (1001)
  │     └── F 用户删除 (1003)
  ── C 角色管理 (101, parent_id=1)
        └── ...
```

**删除的影响**：
- 删除一个菜单（`menu_type=C`），其下所有按钮（`F`）也会失去意义
- 删除目录（`M`），其下所有子菜单和按钮都不可见
- 但 `sys_role_menu` 中的关联记录不会自动清理

## 表6-9：关联表（3张）

> **类比**：这三张表就像"关系登记表"，记录谁和谁有关系。

### `sys_user_role` 用户-角色关联表

```
用户1(admin) ──→ 角色1(超级管理员)
用户2(ry)   ──→ 角色2(普通角色)
```

| 字段 | 含义 |
|------|------|
| `user_id` | 用户编号 |
| `role_id` | 角色编号 |

**联合主键** `(user_id, role_id)`：同一个用户不能重复分配同一个角色。

### `sys_role_menu` 角色-菜单关联表

```
角色2(普通角色) ──→ 菜单1(系统管理)
角色2(普通角色) ──→ 菜单100(用户管理)
角色2(普通角色) ──→ 菜单1000(用户查询)
...
```

记录每个角色拥有哪些菜单和按钮权限。

### `sys_role_dept` 角色-部门关联表

```
角色2(普通角色) ──→ 部门100(若依科技)
角色2(普通角色) ──→ 部门101(深圳总公司)
角色2(普通角色) ──→ 部门105(测试部门)
```

当角色的 `data_scope=2`（自定义数据权限）时，通过这张表指定能访问哪些部门。

### `sys_user_post` 用户-岗位关联表

```
用户1(admin) ──→ 岗位1(董事长)
用户2(ry)   ──→ 岗位2(项目经理)
```

**删除的影响**：
- 删除用户时，需要同时清理 `sys_user_role` 和 `sys_user_post` 中的关联记录
- 删除角色时，需要同时清理 `sys_role_menu` 和 `sys_role_dept` 中的关联记录
- 若依后端代码中已经处理了这些级联删除

## 表10：`sys_oper_log` 操作日志表

> **类比**：公司的"监控录像"，记录谁在什么时候做了什么操作。

| 字段 | 含义 | 为什么需要 |
|------|------|-----------|
| `oper_id` | 日志编号 | 主键 |
| `title` | 模块标题 | 如"用户管理"，知道是哪个模块的操作 |
| `business_type` | 业务类型 | `0`=其它, `1`=新增, `2`=修改, `3`=删除 |
| `method` | 方法名称 | 如 `SysUserController.add()`，定位到具体代码 |
| `request_method` | 请求方式 | `GET`/`POST`/`PUT`/`DELETE` |
| `operator_type` | 操作类别 | `0`=其它, `1`=后台用户, `2`=手机端用户 |
| `oper_name` | 操作人员 | 谁做的这个操作 |
| `dept_name` | 部门名称 | 这个人属于哪个部门 |
| `oper_url` | 请求URL | 访问了哪个接口 |
| `oper_ip` | IP地址 | 从哪里操作的 |
| `oper_location` | 操作地点 | IP对应的地理位置 |
| `oper_param` | 请求参数 | 传了什么参数（如新增用户时传的用户信息） |
| `json_result` | 返回参数 | 接口返回了什么结果 |
| `status` | 操作状态 | `0`=成功, `1`=异常 |
| `error_msg` | 错误消息 | 如果失败了，记录错误信息 |
| `oper_time` | 操作时间 | 什么时候做的 |
| `cost_time` | 消耗时间 | 接口执行花了多少毫秒，用于性能分析 |

**索引说明**：`business_type`、`status`、`oper_time` 建了索引，因为这三个字段最常用于查询过滤。

## 表11-12：字典表（2张）

> **类比**：系统的"翻译本"。数据库里存的是 `0`、`1`、`2` 这样的数字，前端需要显示"男"、"女"、"未知"，字典表就是做这个翻译的。

### `sys_dict_type` 字典类型表（翻译本的"目录"）

| 字段 | 含义 | 举例 |
|------|------|------|
| `dict_id` | 字典编号 | 主键 |
| `dict_name` | 字典名称 | "用户性别" |
| `dict_type` | 字典类型 | `sys_user_sex`（程序用的标识） |
| `status` | 状态 | 停用的字典类型不生效 |

### `sys_dict_data` 字典数据表（翻译本的"内容"）

| 字段 | 含义 | 举例 |
|------|------|------|
| `dict_code` | 字典编码 | 主键 |
| `dict_sort` | 排序 | 控制下拉框中选项的顺序 |
| `dict_label` | 字典标签 | "男"（前端显示的） |
| `dict_value` | 字典键值 | `0`（数据库存的） |
| `dict_type` | 字典类型 | `sys_user_sex`（关联到哪个字典类型） |
| `css_class` | 样式 | 自定义CSS类名 |
| `list_class` | 表格样式 | `primary`=蓝色标签, `danger`=红色标签, `success`=绿色标签 |
| `is_default` | 是否默认 | `Y`=下拉框默认选中这个 |

### 搭配使用示例

```
数据库存: sex = '0'
    ↓ 查字典表 (dict_type = 'sys_user_sex', dict_value = '0')
前端显示: "男"（蓝色标签，因为 list_class = 'primary'）
```

**删除的影响**：
- 删除字典类型 → 其下所有字典数据失效
- 删除字典数据 → 前端显示时会看到原始数字而不是文字

## 表13：`sys_config` 参数配置表

> **类比**：系统的"设置面板"，可以动态调整系统行为，不用改代码。

| 字段 | 含义 | 举例 |

## 表15-16：定时任务表（2张）

> **类比**：公司的"自动提醒系统"，定时自动执行某些任务。

### `sys_job` 定时任务调度表

## 表17-18：通知公告表（2张）

### `sys_notice` 通知公告表

| 字段 | 含义 |
|------|------|
| `notice_id` | 公告编号 |
| `notice_title` | 公告标题 |
| `notice_type` | `1`=通知, `2`=公告 |
| `notice_content` | 公告内容（支持HTML富文本） |
| `status` | `0`=正常, `1`=关闭 |

### `sys_notice_read` 公告已读记录表

| 字段 | 含义 | 搭配作用 |
|------|------|---------|
| `read_id` | 记录编号 | 主键 |
| `notice_id` | 公告编号 | 和 `user_id` 联合，记录谁读了哪条公告 |
| `user_id` | 用户编号 | — |
| `read_time` | 阅读时间 | — |

**唯一约束** `uk_user_notice (user_id, notice_id)`：同一用户同一公告只记录一次，防止重复标记已读。

## 表之间的关系总览

```
sys_dept (部门)
  │
  ├── sys_user (用户) ──→ dept_id 关联
  │     │
  │     ├── sys_user_role ──→ sys_role (角色)
  │     │                          │
  │     │                          ├── sys_role_menu ──→ sys_menu (菜单)
  │     │                          │
  │     │                          └── sys_role_dept ──→ sys_dept (部门，数据权限)
  │     │
  │     └── sys_user_post ─→ sys_post (岗位)
  │
  └── sys_notice_read (公告已读)
        │
        └── sys_notice (公告)

sys_dict_type (字典类型) ──→ sys_dict_data (字典数据)

sys_job (定时任务) ──→ sys_job_log (任务日志)

gen_table (代码生成表) ──→ gen_table_column (代码生成字段)
```

这个全景理解后，你之前创建的 `sys_registration` 表就是在这个体系上扩展的业务表，通过 `user_id` 关联到 `sys_user`，属于"用户的一对多报名记录"。
