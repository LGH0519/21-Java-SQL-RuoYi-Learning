1、理解数据库中的表与界面的关联
表与界面并不是一一对应的，一个界面中需要的数据可以来自多个表。
表应该模块化，单一模块描述。
2、理解人员-角色-菜单之间的联系
给人员设置角色，相当于给人员添加上了某种权限，根据角色获取菜单数据，从而显示不同的界面。如：前台界面、后台管理界面。
3、数据库添加权限标识的作用
数据库表中的权限标识是为了防止有人恶意绕过前端直接像后端发送信息，进行最后的权限判定。
4、新表导入，初期验证步骤
建数据库新表的表结构——>导入到数据库——>在超级管理员界面添加新用户，并给相应角色、菜单——>登录新用户账号，查看新菜单是否出现
5、新账号界面没有显示新菜单
步骤：检查数据库连接是否正确——>在前端网路界面查看getinfo或getRouters响应数据——>根据返回的信息判断查用户--角色--菜单这条链路是否真的通了，是否存在重复角色。
6、前端路径对应关系
菜单中的组件路径不写src/views和.vue便是需要写入数据库中的路由路径。
7、model、rules、prop、ref
`model` 提供数据，`rules` 提供规则，`prop` 把字段和规则对应起来，`ref` 让 JavaScript 能命令整张表单开始校验。
8、点击“个人报名”涉及两段流程：[流程图](流程图.md)
- 登录/刷新时：从后端取得菜单并生成路由。getRouters
- 真正点击菜单时：前端跳转路由并加载Vue页面。
9、Controller——>Service——>Mapper

- Service接口通常有真实的Java实现类，通过Ctrl+Alt+B跳转到实现。
- Mapper接口通常没有java实现类，由MyBatis在运行时动态生成的代理对象。需要手动在资源目录中寻找对应的XML
10、`#{userId}`使用预编译参数，通常安全，也是业务条件的标准写法。`${userId}`进行字符串直接替换，使用不当可能产生SQL注入风险。#{userId}：MyBatis会先生成带占位符的 SQL，是把参数当作“数据值”传给数据库。${userId}：MyBatis会先进行文本替换，是先把参数内容直接拼进 SQL 字符串，再交给数据库执行。
11、开发过程中我认识到，数据库字段变化会影响实体类、Mapper映射、业务逻辑、接口和页面，因此表设计前要尽量明确当前阶段的业务规则，但不应过度预测未来需求，后续应通过迁移SQL逐步演进。
12、package.json本次项目的可执行的命令和依赖（核心依赖Vue3.x和vite）；vite.config.js本项目的配置、插件（基于vite的配置）；main.js入口文件，决定项目是如何跑起来的（createApp函数创建应用实例——>把根组件选出来，挂载到id=app的节点上）；app.vue根组件SFC单文件组件script(脚本) - template(模板) - style(样式)；模板template不再要求唯一根元素，脚本script添加setup标识支持组合式API；index.html单页入口，提供id为app的挂载点
13、Xxxx(() => {}) 把函数作为参数传给 `Xxxx`；`Xxxx` 决定是否调用、何时调用、调用几次以及传入什么数据。外层函数管理执行时机，内层函数描述到时候要做的事情。
14、在若依项目里，`proxy` 经常用于访问挂载到 Vue 组件上的全局方法和属性。
15、`trigger: "blur"`：决定用户操作过程中的自动校验时机。`.validate()`：提交时主动进行完整校验。
