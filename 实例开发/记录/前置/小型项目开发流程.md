你的感受是对的：数据库字段一旦变化，通常会沿着后端和前端整条数据链产生影响。

但需要修正一个容易走向另一个极端的想法：

> 数据库设计应该“尽量合理、覆盖已确认需求”，但不是第一次就把未来可能用到的字段全部加进去。

如果为了避免以后修改，把大量不确定字段提前加入，往往会造成字段含义模糊、长期为空、业务规则混乱。成熟项目并不害怕合理的数据库变更，而是通过“需求分析 + 数据库迁移 + 分层修改”控制变化。

## 一、典型项目开发流程

一个小型报名系统可以按下面的顺序开发：

```
1. 需求分析
   ↓
2. 业务流程设计
   ↓
3. 页面原型和接口草图
   ↓
4. 数据库设计
   ↓
5. 后端接口开发
   ↓
6. 前端页面开发
   ↓
7. 联调和测试
   ↓
8. 部署
   ↓
9. 后续迭代
```

数据库设计主要发生在第4步，但不是只有第4步才允许修改数据库。

项目迭代时可能再次经历：

```
新增需求
   ↓
分析业务变化
   ↓
判断数据库是否需要调整
   ↓
编写数据库迁移SQL
   ↓
修改后端
   ↓
修改前端
   ↓
回归测试
```

所以数据库设计是一项持续工作，只是第一次集中设计通常发生在正式编码之前。

## 二、数据库设计前必须先知道什么

不能一拿到“做一个报名系统”就立即建表。至少要先回答下面的问题。

### 1. 谁使用系统

当前系统至少有：

- 报名人员；
- 管理员。

开发人员不是业务角色。开发人员负责建设和维护系统，不应该作为业务层级与报名人员、管理员并列。

### 2. 用户要完成什么操作

报名人员：

- 查看自己的报名；
- 保存草稿；
- 提交报名；
- 查看审核结果；
- 未来可能撤回报名。

管理员：

- 查询报名列表；
- 查看报名详情；
- 审核报名。

### 3. 数据处于哪些状态

当前状态：

```
草稿 → 待审核 → 审核通过
                 或
                 审核不通过
```

未来如果实现撤回：

```
待审核 → 已撤回
```

状态流程会直接决定数据库的 `status` 字段和后端更新条件。

### 4. 哪些信息必须长期保存

例如：

- 报名属于哪个用户；
- 报名年份；
- 姓名、手机号、职位；
- 当前状态；
- 提交时间；
- 最后一次审核人、审核时间、审核意见。

先明确这些业务事实，才能设计数据库。

## 三、你的认识为什么基本正确

假设现在给 `biz_registration` 新增：

```
audit_opinion varchar(500)
```

通常不只是改数据库。

它可能影响：

|位置|可能需要的修改|
|---|---|
|数据库|添加 `audit_opinion` 列|
|Java实体类|添加 `auditOpinion` 属性及 getter、setter|
|Mapper XML|查询字段和 `resultMap` 增加映射|
|更新SQL|审核时写入该字段|
|Service|校验审核意见|
|Controller|接收或返回审核信息|
|请求对象|添加前端允许提交的审核意见|
|响应对象|添加允许返回的审核信息|
|前端API|必要时调整参数|
|前端页面|增加审核意见输入或展示|
|测试|验证通过、不通过、空意见等情况|

这说明一个重要概念：

> 数据库表不是孤立存在的，它是整个数据交互链的底层组成部分。

在你的项目中，数据通常这样流动：

```
Vue页面
  ↓
前端API
  ↓
Controller
  ↓
Service
  ↓
Mapper.java
  ↓
Mapper.xml
  ↓
数据库
```

查询结果则按相反方向返回。

因此底层字段变化，可能影响上面多个层次。

## 四、是不是第一次就应该把表设计得非常完整

不应该追求“预测所有未来需求”，而应该追求下面三点。

### 1. 已确认的第一阶段功能必须完整

例如第一阶段已经确定管理员要审核，那么下面三个字段就应该提前设计：

```
audit_by
audit_time
audit_opinion
```

如果早已确定需要审核，却等到写审核页面才临时加字段，说明前期业务分析确实不足。

### 2. 稳定的基础关系要提前考虑

例如：

```
user_id
registration_year
```

以及唯一约束：

```
unique key uk_registration_year_user_id
    (user_id, registration_year)
```

它表达了稳定业务规则：

> 一个用户一年只能有一条报名记录。

这种规则应尽量在首次设计时明确，因为它影响整个系统的数据正确性。

### 3. 不确定的未来功能不要提前堆进去

例如目前没有确定要开发：

- 缴费；
- 准考证；
- 成绩；
- 多轮审核；
- 审核历史；
- 短信通知。

就不应立即在主表加入：

```
payment_status
payment_time
exam_number
exam_score
first_audit_by
second_audit_by
sms_status
```

这些字段现在没有明确含义，反而会提高学习和开发难度。

## 五、“可扩展性”不等于“字段越多越好”

真正的可扩展性主要来自以下方面。

### 清晰的主键和关联关系

```
sys_user.user_id
        ↓
biz_registration.user_id
```

明确报名记录属于哪个系统用户。

### 明确的业务唯一性

```
unique key uk_registration_year_user_id
    (user_id, registration_year)
```

### 字段职责单一

例如：

```
status          只表示报名状态
audit_by        只表示最后一次审核账号
audit_time      只表示最后一次审核时间
audit_opinion   只表示最后一次审核意见
```

不要用一个模糊的 `other_info` 字段保存所有内容。

### 允许通过迁移脚本演进

可扩展的系统不是“永远不改表”，而是“可以安全、有记录地改表”。

## 六、原始建表SQL和迁移SQL要区分

这是你接下来需要建立的重要习惯。

### 项目尚未正式使用时

可以调整初始建表文件：

```
01_create_biz_registration.sql
```

因为数据库还只是本地学习数据，可以重新建表。

### 项目已经产生有效数据后

不要再通过：

```
drop table biz_registration;
```

重建表，否则原数据会丢失。

应创建新的迁移文件，例如：

```
02_add_registration_audit_fields.sql
```

内容：

```
alter table biz_registration
    add column audit_by varchar(64) default null comment '审核人登录账号',
    add column audit_time datetime default null comment '审核时间',
    add column audit_opinion varchar(500) default null comment '审核意见';
```

每次数据库结构变化都留下记录：

```
01_create_registration_table.sql
02_add_audit_fields.sql
03_add_attachment_table.sql
```

这样其他开发人员和服务器数据库才知道应该依次执行哪些变化。

## 七、数据库设计时建议完成的检查

以后设计一张业务表，可以按这个顺序检查。

### 第一组：业务对象

- 这张表保存的是什么？
- 一条记录表示什么？
- 主键是什么？
- 和其他表是什么关系？

例如：

```
一条 biz_registration
= 某个用户在某个年份的一次报名
```

### 第二组：业务约束

- 哪些字段必须填写？
- 哪些字段草稿阶段可以为空？
- 是否存在唯一性要求？
- 是否有状态变化？
- 是否允许逻辑删除？

注意：

> 页面必填不一定等于数据库立即 `not null`。

比如真实姓名提交时必填，但保存草稿时可能暂时为空。因此第一阶段设置为允许 `null`，由提交报名的 Service 检查，是合理的。

### 第三组：字段类型

- 年份用什么类型？
- 时间是否需要保存时分秒？
- 字符串最大长度是多少？
- 字典值和实际文字保存哪一个？
- 金额是否使用 `decimal`？

### 第四组：索引

索引应服务于实际查询，例如管理员经常按年度和状态查询：

```
key idx_registration_year_status
    (registration_year, status)
```

不要给每个字段都建立索引。索引会提高查询速度，但也会增加写入和维护成本。

### 第五组：审计字段

业务表通常可以保留：

```
create_by
create_time
update_by
update_time
del_flag
remark
```

具体业务还可以有：

```
submit_time
audit_by
audit_time
audit_opinion
```

两类字段不要混为一谈：

- `update_by`：最后修改这条数据的账号；
- `audit_by`：执行审核业务的管理员账号。

## 八、你当前项目采用什么开发方式更合适

你的目标是学习若依完整数据交互流程，不是一次完成大型报名平台。因此建议使用“纵向小闭环”。

### 第一个闭环：个人报名

```
数据库主表
→ 查询自己的报名
→ 保存草稿
→ 提交报名
→ 前端页面验证
```

你已经基本完成。

### 第二个闭环：管理员查询

```
管理员列表接口
→ 条件查询和分页
→ 管理页面列表
→ 报名详情
```

目前也基本完成。

### 第三个闭环：管理员审核

```
补齐审核字段映射
→ 审核请求对象
→ Controller
→ Service状态校验
→ Mapper条件更新
→ 前端审核弹窗
→ 验证审核结果
```

### 后续扩展

完成基础闭环后，再考虑：

- 撤回报名；
- 附件表；
- 学习经历表；
- 审核历史；
- 准考证；
- 多年度配置。

这种方式既能让每一步跑起来，也不会因为一开始字段太多而看不懂业务代码。

## 九、最终应该形成的正确理解

可以把项目开发理解为三个不断配合的设计：

```
业务设计
决定系统应该做什么
        ↓
数据设计
决定哪些事实需要长期保存
        ↓
程序设计
决定这些数据如何被读取、校验和修改
```

你的结论可以调整为：

> 在数据库设计前，应尽量把当前阶段已经确定的业务流程、状态和数据关系分析完整；但不必预测所有未来功能。后续修改表结构是正常的，只需要通过数据库迁移脚本和分层检查，有计划地同步修改相关代码。

这比“第一次把所有字段都加全”更接近真实项目的开发方式。

可以把这次经历总结成下面这段，适合面试时表达：

> 我基于若依框架开发了一个报名管理模块。首先梳理报名人员和管理员两类角色以及草稿、待审核、审核通过、审核不通过等业务状态，然后设计报名主表、字典和菜单权限。后端按照 Controller、Service、Mapper、数据库的分层完成报名查询、保存草稿、提交报名、管理员分页查询和详情查看；前端使用 Vue 完成表单、列表、分页、字典展示和权限控制。开发过程中我认识到，数据库字段变化会影响实体类、Mapper映射、业务逻辑、接口和页面，因此表设计前要尽量明确当前阶段的业务规则，但不应过度预测未来需求，后续应通过迁移SQL逐步演进。

更简短的版本：

> 我基于若依完成了一个报名管理模块，覆盖数据库表和状态设计、角色菜单权限、后端分层接口以及Vue页面联调。通过这次开发，我理解了前后端完整的数据流，也认识到数据库设计需要覆盖已确定的业务规则，同时通过迁移脚本支持后续迭代，而不是一开始堆砌所有可能字段。
