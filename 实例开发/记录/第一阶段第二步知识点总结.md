# 二、报名状态机

状态机表示一条报名记录可以从什么状态变成什么状态。

| 状态值 | 状态名称 | 报名人员可以执行的操作 | 管理员可以执行的操作 |
|---|---|---|---|
| `0` | 草稿 | 编辑、保存、提交 | 查看 |
| `1` | 待审核 | 查看、撤回 | 查看、审核 |
| `2` | 审核通过 | 查看 | 查看 |
| `3` | 审核不通过 | 查看审核意见、编辑、保存、重新提交 | 查看 |
| `4` | 已撤回 | 编辑、保存、重新提交 | 查看 |

主要状态流转：

```text
草稿 0
  ↓ 提交
待审核 1
  ├─ 管理员审核通过 ─→ 审核通过 2
  ├─ 管理员审核不通过 → 审核不通过 3
  │                         ↓ 修改并重新提交
  │                       待审核 1
  └─ 报名人员撤回 ────→ 已撤回 4
                            ↓ 修改并重新提交
                          待审核 1
```

重要原则：状态迁移必须由后端决定，前端不能直接提交一个 `status` 要求数据库接受。

# 三、先建立“数据住在哪里”的认识

在当前项目中，同一个报名信息会在不同位置以不同形式短暂停留。

| 位置 | 数据形式 | 作用 |
|---|---|---|
| MySQL | `biz_registration` 表中的一行 | 持久保存，服务重启后仍存在。 |
| Java Entity | `BizRegistration` 对象 | 后端运行时表示一条报名记录。 |
| DTO | `RegistrationDraftRequest` 等对象 | 限制前端允许提交的字段。 |
| VO | `RegistrationCurrentResponse` | 限制后端允许返回给个人端的字段。 |
| HTTP JSON | 请求体或响应体 | 在浏览器和后端之间传输。 |
| 前端 API 文件 | `request({...})` | 定义请求地址、方式和参数位置。 |
| Vue `ref()` | `form`、`registrationList` 等 | 页面运行期间保存响应式数据。 |
| Vue 模板 | `v-model`、`{{ }}`、`:data` | 把 JavaScript 数据显示成页面。 |

需要区分：

```text
数据库中的数据       长期保存
Vue ref 中的数据     当前页面打开期间临时保存
HTTP JSON            只负责传输
```

刷新页面后，Vue 内存中的数据会重新创建，因此页面需要再次请求后端，再从数据库查询并回显。

# 四、前后端完整数据流总图

```text
用户操作 Vue 页面
        ↓
Vue 事件处理函数
        ↓
frontend/src/api 中的请求函数
        ↓
HTTP 请求
        ↓
Controller
        ↓
Service 接口
        ↓
ServiceImpl 业务实现
        ↓
Mapper.java
        ↓
Mapper.xml 中的 SQL
        ↓
MySQL
        ↓
查询结果或受影响行数原路返回
        ↓
Controller 包装 JSON 响应
        ↓
前端 API 返回 Promise
        ↓
Vue `.then(response => {...})`
        ↓
修改 ref 响应式数据
        ↓
Vue 自动更新页面
```

记忆口诀：

```text
页面发起 → API 运送 → Controller 接收
→ Service 判断 → Mapper 操作数据库
→ 结果原路返回 → ref 改变 → 页面更新
```

# 五、示例一：打开个人报名页面时，数据怎么流动

## 1. 页面挂载后自动查询

```js
onMounted(() => {
  loadCurrentRegistration()
})
```

`onMounted()` 表示 Vue 组件挂载完成后执行一次。

## 2. Vue 方法调用前端 API

```js
getCurrentRegistration().then(response => {
  Object.assign(form.value, response.data)
})
```

## 3. API 文件生成 HTTP 请求

```js
export function getCurrentRegistration() {
  return request({
    url: "/registration/personal/current",
    method: "get"
  })
}
```

## 4. Controller 接收请求

```java
@GetMapping("/current")
public AjaxResult getCurrentRegistration()
```

Controller 使用 `getUserId()` 获取登录用户，不让前端决定查询哪个用户。

## 5. Service 和 Mapper 查询数据库

```text
selectRegistrationByUserIdAndYear(userId, registrationYear)
```

SQL 使用：

```sql
where user_id = #{userId}
  and registration_year = #{registrationYear}
  and del_flag = '0'
```

## 6. 查询结果返回页面

Controller 将实体中允许个人端查看的字段放入 VO，再返回：

```text
MySQL行
→ BizRegistration
→ RegistrationCurrentResponse
→ JSON
→ response.data
→ form.value
→ 输入框回显
```

# 六、示例二：提交报名时，数据怎么流动

提交并不是只调用一个接口，当前页面采用“先保存，再提交”。

```text
点击提交
  ↓
弹出确认框
  ↓
POST /save-draft 保存页面最新内容
  ↓
POST /submit 修改报名状态
  ↓
GET /current 重新查询
  ↓
页面显示待审核
```

前端 Promise 链：

```js
saveDraft(draftData)
  .then(() => submitRegistration())
  .then(() => loadCurrentRegistration())
```

这里的 `return` 很重要：

```js
return saveDraft(draftData)
```

它让下一段 `.then()` 等待保存成功后再执行。没有 `return` 时，后面的提交可能不会正确等待。

后端提交时负责：

1. 查询本人本年度报名；
2. 判断状态是否允许提交；
3. 校验必填字段；
4. 校验手机号格式和职位字典值；
5. 将状态设为 `1`；
6. 设置提交时间；
7. 重新提交时清空上一轮审核信息；
8. 调用 Mapper 更新数据库。

# 七、示例三：管理员审核时，数据怎么流动

```text
管理员点击审核
  ↓
打开审核弹窗
  ↓
选择审核通过或不通过
  ↓
前端表单校验
  ↓
PUT /registration/manage/{id}/audit
  ↓
Controller 获取管理员登录账号
  ↓
Service 检查记录与状态
  ↓
Mapper 更新 status、audit_by、audit_time、audit_opinion
  ↓
重新查询管理员列表
```

管理员登录账号保存在 `audit_by` 中，它表示“谁进行了审核”，不代表报名人员真实姓名。

审核接口必须检查：

- 审核结果只能是 `2` 或 `3`；
- 审核不通过必须填写意见；
- 报名记录必须存在；
- 只有待审核 `1` 才能审核；
- SQL 中再次使用 `where status = '1'` 防止并发覆盖。

# 八、为什么 Service 检查状态后，SQL 还要检查

Service 中：

```java
if (!"1".equals(registration.getStatus()))
{
    throw new ServiceException("只有待审核状态的报名可以审核");
}
```

SQL 中：

```sql
where registration_id = #{registrationId}
  and status = '1'
```

原因是查询和更新之间，状态可能被另一个操作修改：

```text
管理员A查询到待审核
        ↓
管理员B先审核成功
        ↓
管理员A继续提交旧操作
```

SQL 状态条件可以让管理员A的更新影响 `0` 行，Service 再提示“状态已发生变化”。

这属于简单的并发控制，也叫乐观状态检查。

# 九、撤回和重新提交

## 1. 为什么需要“已撤回”状态

报名人员和管理员都需要区分：

- 是管理员审核不通过；
- 还是报名人员主动撤回。

因此保留 `4 = 已撤回`，而不是直接改回草稿。

## 2. 撤回接口为什么不接收报名ID

个人端撤回使用：

```text
当前登录用户ID + 当前报名年份
```

确定记录，避免用户修改前端参数去撤回其他人的报名。

## 3. 哪些状态允许保存和提交

```text
0 草稿
3 审核不通过
4 已撤回
```

Java 判断：

```java
if (!"0".equals(status)
        && !"3".equals(status)
        && !"4".equals(status))
```

SQL 判断：

```sql
and status in ('0', '3', '4')
```

## 4. 保存和提交的区别

保存只更新用户填写的字段，保持原状态：

```text
已撤回 4 → 保存 → 仍是已撤回 4
```

重新提交才进入待审核：

```text
已撤回 4 → 重新提交 → 待审核 1
```

# 十一、弹窗与路由页面的区别

## 1. 审核使用弹窗

审核字段少、操作时间短，不需要离开列表，因此适合 `el-dialog`。

```text
列表 → 打开审核弹窗 → 提交 → 关闭弹窗 → 刷新列表
```

## 2. 详情使用路由页面

报名详情字段会逐渐增加，以后还会有附件、学习经历等，因此独立页面更合适。

```text
列表页
  ↓ 点击详情
/registration/manage-detail/index/{registrationId}
  ↓
detail.vue
```

## 3. 隐藏路由

详情页需要路由，但不需要在左侧菜单显示，所以配置：

```js
hidden: true
```

## 4. `activeMenu`

详情页打开后，希望左侧仍高亮“报名管理”，因此配置：

```js
meta: {
  activeMenu: "/registrationManage"
}
```

## 5. 路由参数

```js
route.params.registrationId
```

从下面路径中取得最后的报名ID：

```text
/registration/manage-detail/index/3
```

# 十二、`watch()` 与路由参数

详情页面使用：

```js
watch(
  () => route.params.registrationId,
  registrationId => {
    if (registrationId) {
      loadRegistrationDetail(registrationId)
    }
  },
  {
    immediate: true
  }
)
```

三个部分分别表示：

1. `() => route.params.registrationId`：监听什么；
2. `registrationId => {...}`：变化后做什么；
3. `{ immediate: true }`：进入页面时立即执行一次。

使用 `watch()` 的原因是，同一个详情组件切换不同报名ID时，Vue可能复用组件，而不是重新执行 `onMounted()`。

# 十三、Vue 响应式状态

| 写法 | 作用 |
|---|---|
| `ref()` | 创建响应式数据。 |
| `.value` | 在 JavaScript 中读取或修改 ref 的实际值。 |
| `computed()` | 根据其他响应式数据计算新状态。 |
| `watch()` | 在某个响应式数据变化后执行操作。 |
| `onMounted()` | 页面第一次挂载完成后执行操作。 |

## `computed()` 示例

```js
const isEditable = computed(() => {
  return ["0", "3", "4"].includes(
    form.value.status
  )
})
```

它表示：

```text
form.status变化
→ Vue重新计算isEditable
→ 输入框和按钮自动改变禁用状态
```

`computed()` 适合计算结果，不应在里面请求接口或修改数据库。

JavaScript 中读取：

```js
isEditable.value
```

模板中使用：

```vue
:disabled="!isEditable"
```

模板会自动处理 `.value`。

# 十四、`v-loading` 与 `:loading`

| 写法 | 本质 | 作用范围 |
|---|---|---|
| `v-loading="queryLoading"` | Element Plus 指令 | 给页面、表格或卡片增加加载遮罩。 |
| `:loading="saving"` | 向组件传递 loading prop | 只让当前按钮显示加载状态。 |

示例：

```vue
<div v-loading="queryLoading">
  <el-button :loading="saving">
    保存
  </el-button>
</div>
```

对应关系：

```text
页面首次查询 → queryLoading → 整个区域遮罩
点击保存     → saving      → 保存按钮转圈
点击提交     → submitting  → 提交按钮转圈
点击撤回     → withdrawing → 撤回按钮转圈
```

不同操作使用不同变量，避免所有状态都叫 `loading`。

# 十五、组件与 props

组件可以理解成已经封装好的页面功能：

```vue
<el-button />
<el-input />
<dict-tag />
<pagination />
```

props 是父组件传给子组件的输入参数：

```vue
<el-button
  type="primary"
  :loading="saving"
  :disabled="!isEditable"
>
  保存
</el-button>
```

这里的 `type`、`loading`、`disabled` 都是 `el-button` 接收的 props。

静态字符串：

```vue
type="primary"
```

动态 JavaScript 数据：

```vue
:loading="saving"
```

自定义组件使用 `defineProps()` 声明接收的数据：

```js
const props = defineProps({
  status: {
    type: String,
    required: true
  }
})
```

props 是单向数据流，子组件不应该直接修改父组件传入的数据。需要通知父组件时，应使用 `emit`。

# 十六、Element Plus 栅格布局

Element Plus 将一行分成24格：

```vue
<el-row :gutter="24">
  <el-col :xs="24" :md="12">
    真实姓名
  </el-col>

  <el-col :xs="24" :md="12">
    手机号码
  </el-col>
</el-row>
```

含义：

- `el-row`：创建一行；
- `gutter="24"`：列之间留出间距；
- `xs="24"`：小屏幕占满24格；
- `md="12"`：普通电脑屏幕占12格，即一半宽度。

效果：

```text
电脑：真实姓名 | 手机号码
手机：真实姓名
      手机号码
```

栅格布局不是业务功能必需，而是为了两列排版和响应式适配。

# 十七、CSS 中当前需要理解的内容

| CSS | 作用 |
|---|---|
| `display: flex` | 使用弹性布局。 |
| `align-items: center` | 交叉方向居中，横向布局时通常表示垂直居中。 |
| `justify-content: space-between` | 两组内容分别靠左右两端。 |
| `padding` | 元素内部与边框之间的距离。 |
| `margin` | 当前元素与外部元素之间的距离。 |
| `gap` | Flex或Grid子元素之间的间距。 |
| `border` | 边框。 |
| `background-color` | 背景颜色。 |
| `@media` | 根据屏幕宽度应用不同样式。 |
| `:deep()` | 在 scoped 样式中修改子组件内部元素。 |

CSS 需要区分两类：

```text
布局需要：flex、间距、宽度、响应式
纯视觉装饰：颜色、圆角、渐变、阴影
```

纯视觉装饰可以删除或调整，不影响接口和业务流程。

# 二十、加载、禁用和防重复请求

按钮通常同时使用：

```vue
:loading="saving"
:disabled="!isEditable || saving || submitting || withdrawing"
```

页面方法中仍然检查：

```js
if (
  !isEditable.value ||
  saving.value ||
  submitting.value ||
  withdrawing.value
) {
  return
}
```

两处作用不同：

- 模板禁用：改善用户体验；
- 方法检查：防止其他调用方式绕过按钮；
- 后端状态检查：真正的业务安全；
- SQL状态条件：防止并发覆盖。

# 二十二、后端文件职责

| 文件 | 负责内容 |
|---|---|
| `BizRegistrationController` | 个人端请求入口，取得当前用户。 |
| `RegistrationManagementController` | 管理端列表、详情和审核入口。 |

| `BizRegistrationMapper.xml` | 查询、保存、提交、撤回、审核 SQL。 |
| `BizRegistration` | 报名表对应的实体。 |
| `RegistrationDraftRequest` | 个人端允许提交的报名字段。 |
| `RegistrationAuditRequest` | 管理员允许提交的审核字段。 |
| `RegistrationCurrentResponse` | 个人端允许接收的报名与审核字段。 |

# 二十三、忘记数据流时怎么定位

不要从整个项目漫无目的地找。先确定用户做了什么操作。

## 页面按钮没有反应

按顺序检查：

```text
1. Vue按钮是否有 @click
2. 对应方法是否执行
3. 方法是否调用API函数
4. 浏览器Network是否发出请求
```

## 请求404

```text
1. API文件中的url
2. Controller的@RequestMapping
3. 方法上的@GetMapping/@PostMapping/@PutMapping
4. 请求方式是否一致
```

## 请求403

```text
1. 当前账号是否有角色
2. 角色是否有菜单/按钮权限
3. v-hasPermi权限字符
4. @PreAuthorize权限字符
5. 两边字符是否完全一致
```

## 后端报业务错误

```text
1. 查看ServiceException消息
2. 查看当前数据库status
3. 判断当前状态是否允许该操作
```

## 接口成功但数据库没变化

```text
1. Mapper.java方法名
2. Mapper.xml的id
3. SQL where条件
4. 受影响行数是否为0
5. 查看的是不是正确数据库
```

## 数据库正确但页面没变化

```text
1. 操作成功后是否重新查询
2. response.data/rows/total是否读取正确
3. 是否给ref的.value赋值
4. 模板绑定的字段名是否正确
```

## 页面仍显示旧代码

```text
1. 前端开发服务是否重启
2. 浏览器是否强制刷新
3. 修改的是src源码还是dist构建文件
4. 当前运行的是不是另一个项目目录
```

# 二十五、当前阶段最需要记住的内容

不需要背每一个文件中的全部代码，先记住以下六点：

1. Vue 页面不直接访问数据库，只调用前端 API；
2. 前端 API 只负责描述 HTTP 请求，不负责业务判断；
3. Controller 接收请求、获取当前用户并调用 Service；
4. ServiceImpl 是业务规则最集中的地方；
5. Mapper.xml 才包含真正执行的 SQL；
6. 数据返回 Vue 后，修改响应式数据，Vue 才会更新页面。

最简数据流：

```text
Vue → API → Controller → Service → Mapper → MySQL
Vue ← JSON ← Controller ← Service ← Mapper ← MySQL
```

状态操作的四层保护：

```text
页面按钮状态
→ Vue方法再次判断
→ Service业务判断
→ SQL where状态条件
```

# 二十六、推荐复习方式

每次只选择一个操作，例如“撤回报名”，按下面顺序自己讲一遍：

```text
1. 页面哪个按钮触发？
2. Vue中哪个方法执行？
3. 调用了personal.js中的哪个函数？
4. 请求地址和请求方式是什么？
5. 哪个Controller接收？
6. Service检查了什么？
7. Mapper执行了哪条SQL？
8. 数据库哪个字段改变？
9. 前端为什么能显示新状态？
```

能完整讲清一个操作后，再练习“提交报名”“管理员审核”“详情查询”。

这种沿数据流复习的方法，比反复从头阅读所有文件更容易形成长期记忆。
