这些文件属于若依前端的“基础设施层”。你写报名业务时通常只会调用它们，不需要频繁修改。

先记住这条主线：

```
登录成功
  ↓
user Store 保存 Token、用户、角色、权限
  ↓
src/permission.js 路由守卫检查能否进入页面
  ↓
store/modules/permission.js 请求并生成当前用户的路由
  ↓
Sidebar/index.vue 读取侧边栏路由
  ↓
SidebarItem.vue 递归渲染成左侧菜单
  ↓
点击菜单，Vue Router 打开对应 views/*.vue
```

# 一、两份 `permission.js` 不是一回事

## 1. `src/permission.js`：路由守卫

文件：

[src/permission.js](E:/WorkSpace/ruoyi-archive-management/frontend/src/permission.js)

它更准确的名字其实应该是：

```
路由访问控制
```

它负责回答：

```
用户准备进入某个地址时，能不能进入？
进入前还需要做什么？
```

核心代码：

```
router.beforeEach(async (to, from) => {
```

含义是：

```
每次路由跳转之前，都先执行这个函数
```

例如用户准备进入：

```
/registrationManage
```

路由守卫先检查：

1. 有没有 Token；
2. 是否访问登录白名单；
3. 页面是否处于锁屏状态；
4. 用户信息是否已经加载；
5. 动态路由是否已经生成。

### 没有 Token

```
if (getToken()) {
  // 已登录
} else {
  // 未登录
}
```

如果没有 Token，并且目标不是 `/login`，就跳转到：

```
/login?redirect=原地址
```

### 有 Token，但还没有用户信息

```
if (useUserStore().roles.length === 0) {
```

表示刷新页面后，Pinia 内存中的角色还没有重新加载。

于是执行：

```
await useUserStore().getInfo()
```

取得：

- 当前用户；
- 角色；
- 权限字符。

然后执行：

```
const accessRoutes =
  await usePermissionStore().generateRoutes()
```

生成当前用户能访问的动态路由。

最后：

```
router.addRoute(route)
```

将这些路由真正注册到 Vue Router。

### 为什么刷新页面后还要重新查询？

Token 通常保存在 Cookie 中，刷新后仍存在。

但 Pinia 中的：

```
roles
permissions
sidebarRouters
```

是浏览器当前运行内存中的数据，刷新后需要重新获取。

所以流程是：

```
刷新页面
→ Token还在
→ Pinia角色为空
→ 重新查询用户信息
→ 重新生成路由
```

## 2. `store/modules/permission.js`：路由生成和保存

文件：

[store/modules/permission.js](E:/WorkSpace/ruoyi-archive-management/frontend/src/store/modules/permission.js)

它属于 Pinia Store，主要负责：

```
向后端查询路由
→ 转换路由数据
→ 保存侧边栏路由
→ 返回可访问路由
```

它不是路由守卫。

可以这样区分：

|文件|类比|主要职责|
|---|---|---|
|`src/permission.js`|门卫|判断路由跳转时该做什么|
|`store/modules/permission.js`|路由加工厂和仓库|请求、转换、保存路由|

核心入口：

```
generateRoutes() {
```

里面调用：

```
getRouters()
```

向后端请求当前用户菜单。

后端返回的数据大致类似：

```
{
  path: "registrationManage",
  component: "registration/manage/index",
  meta: {
    title: "报名管理",
    icon: "list"
  }
}
```

这时 `component` 还是字符串：

```
registration/manage/index
```

不能直接成为 Vue 组件，所以执行：

```
route.component = loadView(route.component)
```

`loadView()` 会从：

```
import.meta.glob('./../../views/**/*.vue')
```

收集到的页面中找到：

```
views/registration/manage/index.vue
```

最终完成：

```
后端字符串
registration/manage/index

        ↓ loadView()

真正可以加载的Vue组件
views/registration/manage/index.vue
```

转换完成后保存：

```
this.setSidebarRouters(
  constantRoutes.concat(sidebarRoutes)
)
```

这就是左侧菜单的数据来源。

# 二、菜单从数据库到页面的完整流程

```
sys_menu
   ↓
sys_role_menu
   ↓
当前用户拥有的角色
   ↓
后端 GET /getRouters
   ↓
返回路由 JSON
   ↓
store/modules/permission.js
   ↓
filterAsyncRouter()
   ↓
sidebarRouters
   ↓
Sidebar/index.vue
   ↓
SidebarItem.vue
   ↓
左侧菜单
```

因此，你在若依后台修改菜单后，左侧菜单不是直接读取数据库生成 HTML，而是：

```
数据库菜单
→ 后端整理成路由JSON
→ 前端Store保存
→ Vue组件渲染
```

[Sidebar/index.vue](E:/WorkSpace/ruoyi-archive-management/frontend/src/layout/components/Sidebar/index.vue)

# 四、`SidebarItem.vue`：把一条路由画成菜单

文件：

[SidebarItem.vue](E:/WorkSpace/ruoyi-archive-management/frontend/src/layout/components/Sidebar/SidebarItem.vue)

它主要接收三个 props：

```
const props = defineProps({
  item: {
    type: Object,
    required: true
  },
  isNest: {
    type: Boolean,
    default: false
  },
  basePath: {
    type: String,
    default: ""
  }
})
```

含义：

| prop       | 作用              |
| ---------- | --------------- |
| `item`     | 当前准备渲染的路由对象     |
| `isNest`   | 当前菜单是不是嵌套在其他菜单下 |
| `basePath` | 当前菜单的基础路径       |

## 1. 隐藏菜单

```
<div v-if="!item.hidden">
```

如果路由：

```
hidden: true
```

就不显示在侧边栏。

你建立的报名详情路由使用了：

```
hidden: true
```

所以详情页面可以访问，但不会单独出现在菜单中。

## 2. 只有一个可见子菜单

```
hasOneShowingChild(
  item.children,
  item
)
```

若一个父菜单下面只有一个可见子菜单，若依可能直接显示子菜单，减少没有必要的父级折叠。

## 3. 多个子菜单

如果存在多个子项，则显示：

```
<el-sub-menu>
```

然后再次调用自己：

```
<sidebar-item
  v-for="child in item.children"
  :item="child"
/>
```

这叫“递归组件”。

结构类似：

```
系统管理
├── 用户管理
├── 角色管理
└── 菜单管理
```

处理过程：

```
SidebarItem渲染系统管理
    ↓
发现有children
    ↓
再次使用SidebarItem渲染用户管理
    ↓
再次使用SidebarItem渲染角色管理
```

## 4. 路径拼接

```
resolvePath(child.path)
```

用于把父路径和子路径拼起来。

例如：

```
父路径：system
子路径：user
最终：/system/user
```

# 六、`src/plugins` 是什么？

目录：

[plugins](E:/WorkSpace/ruoyi-archive-management/frontend/src/plugins)

这里的 plugin 不是浏览器插件，而是若依给 Vue 页面准备的公共工具。

[plugins/index.js](E:/WorkSpace/ruoyi-archive-management/frontend/src/plugins/index.js) 将工具注册到所有组件：

```

  auth

  cache

  modal
```

因此页面中可以通过：

```

```

使用：

```
proxy.$modal

```

各文件作用如下：

| 文件            | 提供的能力                          | 示例                          |
| ------------- | ------------------------------ | --------------------------- |
| `modal.js`    | 消息、确认框、提示框                     | `proxy.$modal.msgSuccess()` |

## `plugins` 和 `store` 的区别

```
plugins：提供可以调用的公共工具方法
store：保存可以被多个组件共享的状态数据
```

例如：

```

```

是一个工具方法，但它判断权限时读取：

```
user Store中的permissions
```

所以两者会配合，但职责不同。

先记住一句话：

> **Pinia 是 Vue 的状态管理工具；Store 是用 Pinia 创建的数据仓库。**

## 1. Pinia 和 Store 的关系

可以把它们理解成：

|名称|含义|类比|
|---|---|---|
|Pinia|管理全局状态的工具库|银行系统|
|Store|某一类数据的仓库|银行里的账户|
|State|Store 保存的数据|账户余额|
|Getter|根据 State 计算出的数据|余额统计|
|Action|查询或修改 State 的方法|存钱、取钱|

所以：

- 项目一般只安装一个 Pinia。
- Pinia 中可以创建多个 Store。
- 若依的 `user`、`permission`、`app` 都是不同的 Store。

官方文档也将 `state`、`getters`、`actions` 分别类比为组件中的 `data`、`computed`、`methods`。[Pinia：定义 Store](https://pinia.vuejs.org/zh/core-concepts/)

---

## 2. `src/store` 是什么

`src/store` 只是项目里的文件夹名称，用来集中存放状态管理代码：

```
src/store/
├── index.js
└── modules/
    ├── user.js
    ├── permission.js
    ├── app.js
    ├── dict.js
    ├── settings.js
    └── tagsView.js
```

这里容易混淆三个概念：

- `Pinia`：第三方工具库
- `Store`：使用 Pinia 创建的数据仓库
- `src/store`：保存 Store 文件的目录

目录名叫 `store` 只是项目约定，并不是 Vue 的固定语法。

---

## 3. `store/index.js` 做什么

若依中通常类似：

```
import { createPinia } from 'pinia'

const store = createPinia()

export default store
```

它创建的是整个项目的 **Pinia 根实例**。

然后在 `main.js` 注册：

```
import store from './store'

app.use(store)
```

这相当于告诉 Vue：

> 本项目要使用 Pinia，以后各个组件都可以访问其中的 Store。

注意，这里的变量虽然叫 `store`，但它更准确地说是“Pinia 根实例”，并不是 `userStore` 这种具体业务仓库。

## 4. 一个具体 Store 是怎样创建的

例如简化后的用户 Store：

```
import { defineStore } from 'pinia'

const useUserStore = defineStore('user', {
  state: () => ({
    token: '',
    roles: [],
    permissions: []
  }),

  actions: {
    setToken(token) {
      this.token = token
    }
  }
})

export default useUserStore
```

### `defineStore('user', ...)`

表示定义一个 Store：

```
defineStore('user', ...)
```

其中 `'user'` 是这个 Store 的唯一标识。

### `state`

用于保存共享数据：

```
state: () => ({
  token: '',
  roles: [],
  permissions: []
})
```

这些数据可以被多个组件共同使用。

### `actions`

用于放置操作数据的方法：

```
actions: {
  setToken(token) {
    this.token = token
  }
}
```

Action 也可以调用后端接口，并且可以使用 `async/await`。[Pinia：Actions](https://pinia.vuejs.org/core-concepts/actions.html)

```
import useUserStore from '@/store/modules/user'
```

`defineStore()`主要是定义仓库，调用 `useUserStore()` 后才取得这个仓库的实际实例。

## 6. 为什么不全部使用 `ref()`

页面自己的数据适合用 `ref()`：

```
const form = ref({
  realName: '',
  phoneNumber: ''
})

const queryLoading = ref(false)
```

因为报名表单和查询状态主要属于当前页面。

但是下面的数据会被很多地方使用：

```
当前用户是谁
用户拥有哪些角色
用户拥有哪些权限
左侧显示哪些菜单
当前打开了哪些标签页
侧边栏是否收起
```

这些数据不能只放在某一个页面中，因此适合放进 Pinia Store。

简单判断：

|数据|放在哪里|
|---|---|
|当前页面表单|`ref()`|
|当前弹窗是否显示|`ref()`|
|当前页面查询状态|`ref()`|
|登录用户信息|`userStore`|
|用户权限|`userStore`|
|动态菜单和路由|`permissionStore`|
|侧边栏状态|`appStore`|
|已打开的标签页|`tagsViewStore`|

不要看到数据就放进 Store。**只有多个组件需要共享，或者跨路由仍然需要使用的数据，才优先考虑 Store。**

---

## 7. 若依中的实际数据流向

登录后的主要流程可以这样理解：

```
用户登录
   ↓
后端返回 token
   ↓
userStore 保存 token
   ↓
进入新页面，触发 src/permission.js
   ↓
userStore.getInfo()
   ↓
后端返回用户、角色、权限
   ↓
保存到 userStore
   ↓
permissionStore.generateRoutes()
   ↓
后端返回菜单路由
   ↓
保存到 permissionStore.sidebarRouters
   ↓
Sidebar 读取 sidebarRouters
   ↓
SidebarItem 递归显示左侧菜单
```

因此：

- `userStore` 管“当前登录用户是谁、拥有什么权限”。
- `permissionStore` 管“根据权限应该生成什么路由和菜单”。
- `Sidebar` 负责把菜单数据展示出来。
- `src/permission.js` 负责把这些步骤串联起来。

## 8. Store 和数据库不是一回事

这是初学时很容易混淆的一点：

```
MySQL数据库：长期保存业务数据
后端Java对象：处理一次请求的数据
Pinia Store：浏览器运行期间共享的前端数据
Vue组件ref：当前页面自己的数据
```

Pinia 中的数据通常保存在浏览器内存里，刷新页面后可能消失。

若依刷新以后还能保持登录，主要因为：

1. token 被保存在 Cookie 或本地存储中；
2. 页面刷新后重新读取 token；
3. 再调用 `getInfo()` 获取用户、角色和权限；
4. 再次生成动态路由。

不是因为 Pinia 默认永久保存了所有数据。

你目前可以先把它记成：

> `ref` 管一个页面的数据，Store 管多个页面共同需要的数据，后端和数据库负责真正持久化数据。

这三行看起来很像，但分别对应三个不同动作：

```
const useUserStore = defineStore(...)
import useUserStore from '@/store/modules/user'
const userStore = useUserStore()
```

可以理解为：**定义 → 导入 → 使用**。

## 1. 定义 Store

在 `src/store/modules/user.js` 中：

```
const useUserStore = defineStore('user', {
  state: () => ({
    token: '',
    roles: [],
    permissions: []
  }),

  actions: {
    setToken(token) {
      this.token = token
    }
  }
})
```

`defineStore()` 是 Pinia 提供的函数：

```
defineStore('user', 配置对象)
```

执行后，它返回一个“获取用户 Store 的函数”，保存到：

```
const useUserStore
```

此时的 `useUserStore` 不是用户数据本身，可以暂时把它理解为：

> 用来取得用户仓库的入口函数。

然后导出：

```
export default useUserStore
```

完整写法是：

```
import { defineStore } from 'pinia'

const useUserStore = defineStore('user', {
  state: () => ({
    token: '',
    roles: [],
    permissions: []
  })
})

export default useUserStore
```

---

## 2. 导入 Store 函数

在其他文件中：

```
import useUserStore from '@/store/modules/user'
```

这行导入的是 `user.js` 默认导出的内容：

```
export default useUserStore
```

可以对应起来看：

```
// user.js
export default useUserStore
```

```
// 其他文件
import useUserStore from '@/store/modules/user'
```

其中：

```
@
```

通常代表：

```
frontend/src
```

所以该路径基本相当于：

```
import useUserStore from '项目路径/frontend/src/store/modules/user'
```

导入文件时通常可以省略 `.js`。

---

## 3. 取得 Store 实例

```
const userStore = useUserStore()
```

这里才真正调用了 `useUserStore()`，取得可以使用的用户 Store 实例。

取得以后才能访问数据和方法：

```
userStore.token
userStore.roles
userStore.permissions

userStore.getInfo()
userStore.setToken(token)
userStore.logOut()
```

注意大小写：

```
useUserStore    // 获取 Store 的函数
userStore       // 调用后得到的 Store 实例
```

这不是语法强制规定，而是常用命名约定：

- `useXxxStore`：表示这是一个获取 Store 的函数。
- `xxxStore`：表示这是已经获得的 Store 实例。

## 完整执行过程

### `user.js`

```
import { defineStore } from 'pinia'

const useUserStore = defineStore('user', {
  state: () => ({
    username: '',
    roles: []
  }),

  actions: {
    setUsername(username) {
      this.username = username
    }
  }
})

export default useUserStore
```

### 某个 Vue 组件

```
<script setup>
import useUserStore from '@/store/modules/user'

// 取得用户 Store 实例
const userStore = useUserStore()

// 读取 state
console.log(userStore.username)

// 调用 action
userStore.setUsername('admin')
</script>
```

完整关系是：

```
defineStore()
    ↓ 返回
useUserStore 函数
    ↓ export default
从 user.js 导出
    ↓ import
在其他文件中导入 useUserStore
    ↓ 调用 useUserStore()
得到 userStore 实例
    ↓
读取 state、getter，调用 action
```

## 用“工具箱”类比

```
const useUserStore = defineStore(...)
```

相当于定义了一种“用户工具箱”的取得方式。

```
import useUserStore from '@/store/modules/user'
```

相当于把取得工具箱的方法带到当前文件。

```
const userStore = useUserStore()
```

相当于真正拿到工具箱。

```
userStore.getInfo()
```

相当于使用工具箱中的工具。

最需要记住的是：

```
useUserStore        // 函数
useUserStore()      // 调用函数
userStore           // 调用后得到的 Store 实例
userStore.roles     // Store 中的数据
userStore.getInfo() // Store 中的方法
```
