下面整理的是你在“个人报名第一阶段”开发过程中实际遇到或讨论过的知识点，按学习顺序分类。每项只做简短解释，方便以后逐项复习。

# 一、若依系统整体结构

|知识点|简短解析|
|---|---|
|若依的定位|若依主要提供后台管理基础能力，例如用户、角色、菜单、权限、字典和代码生成。业务功能需要自己开发。|
|报名人员端与管理端|可以共用一套若依系统，但使用不同角色、菜单、权限和业务接口。|
|`sys_user`|保存所有可以登录系统的账号，既可以包含管理员，也可以包含报名人员。|
|`sys_role`|定义用户属于什么角色，例如 `admin`、`applicant`。|
|`sys_user_role`|建立用户与角色之间的关联。|
|业务角色|报名人员、审核人员、管理员属于业务角色，不是程序的技术分层。|
|技术分层|前端、Controller、Service、Mapper、数据库属于软件技术分层。|
|开发人员|开发人员通常不是业务角色，不需要专门设计“开发人员层”。|
|登录后显示不同界面|若依根据当前用户拥有的角色和菜单权限，动态返回路由和菜单。|
|无注册入口的报名网站|账号可能由主管单位统一导入、预先创建，或者通过其他系统同步。|
|当前登录用户|后端通过登录令牌取得当前用户，不能相信前端传来的 `userId`。|

# 二、若依菜单与权限

| 知识点                | 简短解析                                                    |
| ------------------ | ------------------------------------------------------- |
| `sys_menu`         | 同时保存菜单、页面入口和按钮权限。                                       |
| `menu_type = 'M'`  | 目录类型。                                                   |
| `menu_type = 'C'`  | 页面菜单类型。                                                 |
| `menu_type = 'F'`  | 按钮权限类型。                                                 |
| `parent_id`        | 表示菜单的父子关系；一级菜单通常使用 `0`。                                 |
| `path`             | 前端路由地址。                                                 |
| `component`        | 对应 `src/views` 下的 Vue 页面路径。                             |
| `perms`            | 权限标识，例如 `registration:personal:save`。                   |
| `sys_role_menu`    | 建立角色与菜单、按钮权限之间的关系。                                      |
| 前端权限               | `v-hasPermi` 控制按钮是否显示，主要改善页面体验。                         |
| 后端权限               | `@PreAuthorize` 真正阻止无权限用户调用接口。                          |
| 前后端权限一致            | Vue 中的权限字符串必须与 Controller 中的权限字符串一致。                    |
| 管理端权限分离            | 管理端应使用 `registration:manage:*`，不能复用个人端权限。               |
| 菜单创建者 `admin`      | 初始化 SQL 是由管理员执行的，所以 `create_by` 写 `admin` 合理，不代表当前业务用户。 |
| `permission.js`    | 根据后端菜单动态加载 Vue 页面组件。                                    |
| `import.meta.glob` | 会扫描 `src/views` 下的 Vue 文件，因此参考页面放在该目录也可能进入构建。           |

# 三、数据库建模

|知识点|简短解析|
|---|---|
|业务表与系统表|`biz_registration` 保存报名业务数据；`sys_*` 保存若依系统配置。|
|主键|`registration_id` 唯一标识一条报名记录。|
|`bigint`|常用于主键和用户ID，与若依的 `user_id` 类型保持一致。|
|`smallint`|可以保存报名年份，例如 `2026`。|
|`varchar`|保存长度可变的字符串，例如姓名、手机号和字典值。|
|`char(1)`|适合长度固定的单字符状态值。|
|`datetime`|保存提交时间、创建时间和更新时间。|
|`null`|表示尚未填写或尚未发生，例如草稿的提交时间。|
|`not null`|表示数据库层面不允许缺少该值。|
|默认值|用于创建记录时自动填入初始值，例如 `status = '0'`。|
|不是所有字段都要 `not null`|草稿允许字段不完整，因此姓名、手机号等可以暂时为 `null`。|
|数据库必填与业务必填|数据库是否允许空和“提交报名时必须填写”是两个不同概念。|
|逻辑删除|`del_flag` 表示记录是否删除，而不是直接物理删除。|
|审计字段|`create_by`、`create_time`、`update_by`、`update_time` 用于记录谁在何时操作。|
|唯一约束|`(user_id, registration_year)` 保证同一用户同一年只能有一条报名记录。|
|业务层检查|用于返回友好提示，但不能完全代替数据库唯一约束。|
|普通索引|提高经常使用的查询条件的检索效率。|
|联合索引|将多个经常一起查询的字段放进一个索引。|
|字段长度一致|Java 校验的最大长度应与数据库字段长度一致。|
|字段注释|用于说明字段含义，不影响程序执行，但应尽量准确。|
|修改 SQL 文件|只修改文件不会改变已经建立的数据库，还要执行 `alter table`。|

# 四、报名表设计

|知识点|简短解析|
|---|---|
|`registration_year`|区分不同年度的报名。|
|`user_id`|关联当前登录的若依用户。|
|`real_name`|报名者真实姓名，草稿可空，提交时必填。|
|`phone_number`|手机号码适合用字符串保存，不能用数字类型。|
|`apply_position`|保存报考职位的字典值，而不是页面显示的字典标签。|
|`status`|保存报名当前所处的业务状态。|
|`submit_time`|只有正式提交后才设置。|
|`remark`|保存报名者填写的补充说明。|
|一人一年一条|通过用户ID和报名年份共同确定唯一报名记录。|
|附件表|一条报名可能有多个附件，因此附件更适合独立成表。|
|学习经历表|一名报名者可能有多段学习经历，因此适合一对多附表。|
|独立职位表|将来职位包含部门、人数、专业要求时，应由字典升级为业务表。|

# 五、若依字典

| 知识点               | 简短解析                                            |
| ----------------- | ----------------------------------------------- |
| `sys_dict_type`   | 定义字典类别，例如 `registration_status`。                |
| `sys_dict_data`   | 保存某个字典类型下的具体选项。                                 |
| `dict_label`      | 页面显示的文字，例如“待审核”。                                |
| `dict_value`      | 数据库和前端实际传递的值，例如 `"1"`。                          |
| 字典字段使用字符串         | 若依的 `dict_value` 本身是字符串，因此业务字段通常也使用字符类型。        |
| 字典不是外键            | 字典配置不会自动约束业务表中的值是否合法。                           |
| 后端字典校验            | 需要在 Service 中检查前端传入的值是否属于正常启用的字典项。              |
| 字典缓存              | 若依会缓存字典数据，修改字典后可能需要刷新缓存。                        |
| `data_scope` 没有字典 | `sys_role.data_scope` 是框架内部固定编码，不一定为每个编码建立若依字典。 |

# 六、SQL基础

|知识点|简短解析|
|---|---|
|`create table`|创建数据库表。|
|`drop table if exists`|表存在时先删除，多用于可重复执行的初始化脚本。|
|`insert into ... values`|直接插入明确给出的数据。|
|显式列名|插入时列出字段名，避免表结构变化导致数据错位。|
|多行 `values`|一条语句可以插入多条字典或菜单数据。|
|`insert ... select`|将查询结果直接作为新增数据来源，不是 MySQL 独有语法。|
|`last_insert_id()`|取得本连接最近一次自增插入产生的主键。|
|SQL变量|`set @变量名 = ...` 可以暂存菜单ID、角色ID等值。|
|`alter table`|修改已经存在的表结构。|
|`update`|修改现有记录。|
|`where`|限定查询或更新的目标范围。|
|SQL事务|多条必须一起成功的操作可以放进同一事务。|
|执行脚本与测试脚本|正式创建结构的 SQL 和验证数据的 SQL 应分开放置。|

# 七、后端分层

|层|作用|
|---|---|
|Controller|接收 HTTP 请求、取得当前登录用户、调用 Service、返回响应。|
|Service 接口|声明业务层能够提供哪些能力。|
|Service 实现|实现状态判断、字段校验和业务流程。|
|Mapper.java|声明数据库操作方法。|
|Mapper.xml|编写真正执行的 SQL。|
|Domain/Entity|表示数据库中的业务实体。|
|Request/DTO|表示允许前端向某个接口提交的数据。|
|Response/VO|表示后端允许返回给前端的数据。|

# 九、接口设计

|知识点|简短解析|
|---|---|
|REST接口路径|使用资源和动作表达接口含义。|
|kebab-case|URL 多单词推荐使用 `save-draft`，而不是 `saveDraft`。|
|当前报名接口|`GET /registration/personal/current` 查询当前用户本年度报名。|
|保存草稿接口|`POST /registration/personal/save-draft` 保存可编辑内容。|
|提交报名接口|`POST /registration/personal/submit` 将草稿变为待审核。|
|个人端接口|只能处理当前登录用户自己的数据。|
|管理端接口|应使用独立路径，例如 `/registration/manage/**`。|
|不需要通用 CRUD|业务明确时，`saveDraft`、`submitRegistration` 比通用 `insert`、`update` 更清楚。|
|无用接口|生成器生成的 `add`、`edit`、`getInfo`、`list` 不一定都需要保留。|
|请求|前端发送给后端的数据称为 Request。|
|响应|后端返回给前端的数据称为 Response。|
|参数命名|`registrationDraftRequest` 比 `request` 更具体。|
|业务对象命名|`registrationDraft` 比 `draft` 更容易理解。|
|操作账号命名|`operatorUsername` 明确表示它用于记录操作人。|

# 十、DTO与VO

|知识点|简短解析|
|---|---|
|DTO的作用|限制接口允许接收的字段，避免前端提交 `userId`、`status` 等系统字段。|
|DTO不是运行必需|直接接收实体也能运行，但接口边界不够清楚。|
|VO的作用|限制后端返回给前端的字段，避免暴露无关系统字段。|
|实体与接口对象分离|数据库结构变化时，不会自动改变前后端接口。|
|手动字段转换|当前字段较少，Controller 中手动 `set` 最容易理解。|
|不过度抽象|当前不需要引入映射框架或通用转换器。|

# 十一、Service业务逻辑

|知识点|简短解析|
|---|---|
|保存草稿|没有记录时新增，有记录时更新。|
|草稿允许不完整|保存时不要求姓名、手机号和职位全部填写。|
|提交必须完整|提交时检查姓名、手机号、职位等必填信息。|
|手机号格式校验|使用正则表达式检查基本手机号格式。|
|状态检查|只有 `status = '0'` 的草稿允许修改和提交。|
|字段白名单|更新时只复制用户允许修改的字段。|
|系统字段后端设置|用户ID、年份、状态、审计字段不能由前端决定。|
|`ServiceException`|业务条件不满足时返回可理解的错误信息。|
|私有校验方法|重复使用的职位校验可以封装为 `validateApplyPosition()`。|
|依赖注入|Service 可以注入 Mapper 或其他 Service，例如字典服务。|
|接口与实现|接口说明“能做什么”，实现类说明“具体怎么做”。|

# 十二、MyBatis与Mapper

| 知识点                | 简短解析                                   |
| ------------------ | -------------------------------------- |
| Mapper接口方法         | Java 代码通过它调用数据库操作。                     |
| XML `id`           | 必须与 Mapper.java 的方法名完全一致。              |
| `resultMap`        | 定义数据库字段与 Java 属性的对应关系。                 |
| 下划线与驼峰             | `registration_id` 对应 `registrationId`。 |
| `<sql>`            | 提取可以复用的 SQL 片段。                        |
| `<include>`        | 引入公共 SQL 片段。                           |
| `#{参数}`            | 使用预编译参数，避免直接拼接 SQL。                    |
| `@Param`           | 为 Mapper 的多个参数明确命名。                    |
| `useGeneratedKeys` | 插入成功后，将数据库生成的自增主键写回实体。                 |
| 静态 SQL             | 字段固定时比大量动态 `<if>` 更简单清楚。               |
| 动态 SQL             | 查询条件可选时，可以使用 `<if>` 和 `<where>`。       |
| 编译不能检查 XML 完整性     | Mapper XML 缺少语句时可能编译成功，但运行时报错。         |

# 十三、状态与并发控制

|知识点|简短解析|
|---|---|
|状态机|报名数据按照草稿、待审核、审核通过等状态流转。|
|草稿状态|`0`，可以继续保存和提交。|
|待审核状态|`1`，已提交，报名人员暂时不能修改。|
|审核通过|`2`。|
|审核不通过|`3`。|
|已撤回|`4`，当前阶段暂不实现。|
|状态迁移|提交操作只允许 `0 → 1`。|
|SQL状态条件|`where status = '0'` 防止重复提交或并发修改。|
|受影响行数|更新结果为 `0` 可能表示状态已经变化。|
|前端禁用不是安全措施|后端和 SQL 仍必须检查状态。|
|重复点击|使用 `saving`、`submitting` 和禁用条件防止重复请求。|

# 十五、前端API与异步流程

| 知识点              | 简短解析                                            |
| ---------------- | ----------------------------------------------- |
| API文件            | 集中定义页面调用的后端请求。                                  |
| `request()`      | 若依封装的 Axios 请求工具。                               |
| `params`         | 通常用于 GET 查询参数。                                  |
| `data`           | 通常用于 POST、PUT 请求体。                              |
| Promise          | 表示一个尚未完成的异步请求。                                  |
| `.then()`        | 上一步成功后执行。                                       |
| `.catch()`       | 接收请求失败或取消确认框。                                   |
| `.finally()`     | 无论成功或失败都执行，适合关闭加载状态。                            |
| `return Promise` | 保证多个异步操作按顺序执行。                                  |
| 页面回显             | 查询成功后使用 `Object.assign()` 将数据放入表单。              |
| 保存后重查            | 使用数据库最新结果刷新页面，避免前端状态与数据库不一致。                    |
| 提交前保存            | 先保存当前页面内容，再提交，防止提交旧草稿。                          |
| 查询加载与保存加载        | `queryLoading`、`saving`、`submitting` 应分别表示不同操作。 |

# 十六、前后端校验

|知识点|简短解析|
|---|---|
|前端校验|提前提示用户，改善操作体验。|
|后端校验|防止绕过页面直接提交非法数据。|
|数据库约束|最后一道数据完整性保障。|
|`@Size`|校验字符串长度。|
|`@NotBlank`|拒绝 `null`、空字符串和纯空格。|
|草稿不使用 `@NotBlank`|草稿允许暂时不完整。|
|提交时业务校验|在 Service 中检查最终必填规则。|
|长度一致|`@Size(max=32)` 应与 `varchar(32)` 对应。|
|字典合法性|长度正确不代表字典值一定存在。|
|多层校验并不重复|前端负责体验，Service负责业务，数据库负责最终约束。|

# 十七、管理员界面设计

| 知识点             | 简短解析                                                     |
| --------------- | -------------------------------------------------------- |
| 管理员不是替报名者填表     | 管理端不应直接复用个人端的新增和修改功能。                                    |
| 管理端第一步          | 先做分页列表和条件查询。                                             |
| 管理端第二步          | 增加报名详情查看。                                                |
| 管理端第三步          | 增加审核通过、审核不通过。                                            |
| 管理端通常不物理删除      | 报名记录属于业务凭证，不应随意删除。                                       |
| 管理端默认筛选         | 可以默认显示待审核，同时允许查询其他状态。                                    |
| 管理端独立API        | 建议使用 `frontend/src/api/registration/manage.js`。          |
| 管理端独立页面         | 建议使用 `frontend/src/views/registration/manage/index.vue`。 |

# 十九、项目文件与版本管理

|知识点|简短解析|
|---|---|
|`target`|Maven生成的编译产物，通常不应提交到Git。|
|`dist`|前端构建产物，通常也不作为源码提交。|
|`.gitignore`|用于排除不应提交的编译文件和临时文件。|
|工作区已有修改|检查代码时不能误删用户原有文件。|
|参考页面位置|不参与运行的 Vue 参考文件最好移出 `src/views`。|
|文件移动|Controller 从 `ruoyi-system` 移到 `ruoyi-admin` 属于合理调整。|
|构建产物不能手改|应修改 `src/main` 源码，而不是 `target/classes` 中的文件。|

# 二十、第一阶段最重要的完整数据流

你已经实际跑通了这条链路：

```
Vue页面
  ↓
前端API
  ↓
HTTP请求
  ↓
Controller
  ↓
Service接口
  ↓
Service实现
  ↓
Mapper.java
  ↓
Mapper.xml
  ↓
MySQL
  ↓
查询结果原路返回
  ↓
Vue页面回显
```

第一阶段真正掌握的核心不是“写了几个字段”，而是理解了：

1. 数据从哪里来；
2. 每一层负责什么；
3. 当前用户身份由谁决定；
4. 哪些字段允许前端控制；
5. 业务状态在哪里检查；
6. 数据最终如何进入数据库；
7. 数据又如何返回页面。

接下来开发管理界面，本质上还是同一条数据交互链路，只是换成了管理员权限、列表查询和审核业务。
