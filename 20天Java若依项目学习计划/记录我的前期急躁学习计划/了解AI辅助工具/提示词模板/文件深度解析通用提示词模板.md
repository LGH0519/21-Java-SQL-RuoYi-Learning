# 文件深度解析通用提示词模板

```
# [文件路径] 完整解析

请对我指定的文件进行完整、详尽、通俗易懂的解析。

## 解析对象
- 文件路径：[填写文件的完整路径]
- 文件类型：[自动识别，如 XML / YML / Java / Vue / SQL / JSON / Properties 等]

## 输出要求

请严格按照以下六个维度组织内容，贯穿全文保持一致的解释风格：

---

### 维度一：前置知识（文件定位）

在正式解析之前，先回答三个问题：
1. **这个文件是什么？** —— 用一句话说明文件的本质用途
2. **它在项目中扮演什么角色？** —— 说明它在整个工程中的位置和作用
3. **它和其他文件是什么关系？** —— 说明它与关联文件的协作方式（如有）

要求：
- 必须使用生活化类比来帮助理解（如"管家""说明书""通讯录""采购清单"等）
- 如果该文件属于某一类配置文件/代码文件，先简要解释这类文件/代码的通用概念
- 目标：让完全没有技术背景的人也能明白"这个文件是干什么用的"

---

### 维度二：逐段/逐行详细解释

将文件按功能划分为若干"部分"（Part），每个部分按以下格式输出：

#### 每个部分必须包含：

1. **对应代码**：原文引用该段的代码
2. **逐行解释**：每一行/每一个配置项的具体含义
3. **专有名词通俗化**：
   - 该段中出现的所有技术术语、专有名词，在**首次出现时**必须给出通俗解释
   - 必须附带生活化类比（如"就像快递公司的分拣员……"）
   - 绝对不要假设读者已经知道任何术语
4. **表格辅助**（如适用）：如果该段包含多个并列的配置项/参数，用表格汇总展示（参数名 | 值 | 通俗解释 | 类比）

#### 禁忌词汇：
严禁使用"显然"、"很容易理解"、"不言而喻"、"众所周知"等假设读者已知的表述。

---

### 维度三：可修改项分析与举例

对文件中**每一个可以修改的配置项/代码段**，提供以下分析：

1. **修改示例**：给出修改前和修改后的代码对比
2. **影响分析**：修改后会导致什么变化？需涵盖：
   - 代码运行层面的变化
   - 外观界面/行为上的变化（如有）
   - 对其他模块/文件的连锁影响（如有）
3. **实际开发中需要改吗？**：用以下三级标记说明：
   - ✅ **需要改**：部署/开发时必须修改的项
   - ⚠️ **看情况改**：根据具体场景决定
   - ❌ **不需要改**：保持默认即可

格式示例：

#### 配置项名称

修改前：[原代码]
修改后：[新代码]

影响：
- 修改前：……
- 修改后：……
- 外观界面：……
- 代码运行：……

实际产品开发中需要改吗？ ✅/⚠️/❌ ……


---

### 维度四：段落通俗总结

在每个部分（维度二中的每个 Part）的末尾，必须附带一个"📝 通俗总结"区块：
- 用 2-5 句话，以最通俗的语言概括该部分做了什么
- 必须包含至少一个生活化类比
- 说明在实际开发中是否需要关注/修改该部分

格式示例：

### 📝 通俗总结

> 这 N 行代码做了两件事：
> 1. ……（通俗描述）
> 2. ……（通俗描述）
>
> 类比：就像……
>
> 在实际开发中，……（是否需要修改的建议）


---

### 维度五：全文速查表与总览

在文档末尾提供结构化的速查信息：

1. **配置/代码区域一览**（表格）：
   | 区域 | 行号 | 核心作用 | 是否需要修改 |
   |------|------|---------|-------------|

2. **关键数值/参数速查**（如适用）：
   列出所有关键参数及其含义、默认值、建议值

3. **注意事项/必改清单**（如适用）：
   按优先级排列需要修改的项（🔴 最高 / 🟡 高 / 🔵 中）

---

### 维度六：最终总结

在文档最末尾写一段"最终总结"：
- 用 5-10 句话，从全局视角总结整个文件的功能和地位
- 说明该文件与项目其他部分的关系
- 给出从开发到部署的修改建议概要
- 以生活化类比收尾

---

## 语言与排版风格要求

1. **受众定位**：面向非计算机专业人员或刚接手项目的新人
2. **类比优先**：每个抽象概念首次出现时，必须用生活化类比解释
3. **排版规范**：使用清晰的 Markdown 标题层级（H2/H3/H4）、加粗、列表和代码块
4. **禁忌词汇**：严禁使用"显然"、"很容易理解"、"不言而喻"、"众所周知"等表述
5. **宁可多说**：对任何术语，宁可多解释一句，也不要省略
6. **中英文对照**：技术术语首次出现时标注英文全称（如有）
```

## 使用方法

### 场景一：解析单个配置文件

```
请按照"文件深度解析通用提示词模板"，对以下文件进行完整解析：
[粘贴文件路径 或 直接粘贴文件内容]
```

### 场景二：解析代码文件（Java / Vue / JS 等）

```
请按照"文件深度解析通用提示词模板"，对以下代码文件进行完整解析：
[粘贴文件路径]

额外要求：
- 对每个方法/函数单独解释其输入、输出、核心逻辑
- 说明该类/组件在整个项目中被谁调用、调用了谁
```

### 场景三：解析 SQL 文件

```
请按照"文件深度解析通用提示词模板"，对以下 SQL 文件进行完整解析：
[粘贴文件路径]

额外要求：
- 对每条 SQL 语句解释其目的和效果
- 说明表与表之间的关系（外键、关联字段）
- 用 Mermaid 绘制表关系图
```

### 场景四：解析整个目录/模块

```
请按照"文件深度解析通用提示词模板"的思路，对以下目录进行整体解析：
[粘贴目录路径]

额外要求：
- 先列出目录结构总览
- 按文件/子目录分组解析
- 用 Mermaid 绘制模块内部关系图
- 说明该目录在整个项目中的职责边界
```

### 场景五：对比两个文件

```
请对以下两个文件进行对比解析：
文件 A：[路径A]
文件 B：[路径B]

对比维度：
- 相同点
- 不同点
- 各自的适用场景
- 它们之间的协作关系
```

## 模板设计理念

| 维度 | 对应的问题 | 解决的问题 |
|------|-----------|-----------|
| 维度一：前置知识 | "这个文件是干什么的？" | 建立整体认知 |
| 维度二：逐段解释 | "每一行是什么意思？" | 理解细节含义 |
| 维度三：可修改项 | "哪里能改？改了会怎样？" | 指导实际修改 |
| 维度四：段落总结 | "这段到底说了啥？" | 加深理解、方便回顾 |
| 维度五：速查表 | "快速查找某个配置" | 提高查阅效率 |
| 维度六：最终总结 | "整体来看这个文件怎么样？" | 全局视角收尾 |

> 这个模板的核心思路是 **"从宏观到微观，再从微观到宏观"**——先告诉你文件是什么（宏观），再逐行解释细节（微观），最后用速查表和总结回归全局（宏观）。每个技术概念都用生活类比确保非专业人员也能看懂。
