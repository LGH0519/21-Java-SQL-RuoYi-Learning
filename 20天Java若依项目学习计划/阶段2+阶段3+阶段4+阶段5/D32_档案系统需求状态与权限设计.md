# D32｜档案系统需求、状态与权限设计

> 今日目标：不写业务代码。先完成可审查的需求、角色矩阵、状态图与权限编码；任何功能都能回答“谁操作、改哪张表、状态怎么变”。

## 1. 知识速记

- 第一版固定角色：普通员工、档案管理员、系统管理员。
- 固定范围：分类、档案、附件、检索、申请/撤销、审批/驳回、借出、归还、状态、逾期列表、若依日志/权限。
- 状态分两条：申请 `已提交→已批准/已驳回/已撤销`；借阅 `借阅中→已归还`，到期未还可标 `逾期`。
- 权限编码按资源:动作，例如 `archive:record:add`；禁止用“管理员页面隐藏”代替后端检查。

## 2. 资料

- [若依 Vue：权限控制](https://doc.ruoyi.vip/ruoyi-vue/document/htsc.html)（从官方目录进入权限/菜单章节）。
- D22、D30 的权限双保险笔记。

## 3. 知识详解

状态不是显示文字，而是数据库规则。申请被撤销后不能审批；已驳回不能借出；档案借阅中不能再次发起申请或删除。先写清非法转换，后续 AI 才能生成可审查的 Service 规则。系统管理员负责用户/角色/菜单，不应自动获得档案业务操作的所有权，具体授权仍由菜单/权限配置决定。

## 4. 今天照做

### 09:00–12:00｜写需求骨架

1. 在项目根目录建立 `docs\design\`（若已有则复用）；新建 `requirements.md`。
2. 粘贴并逐项填充：

```md
# 档案管理系统 V1 需求
## 角色矩阵
| 功能 | 普通员工 | 档案管理员 | 系统管理员 |
|---|---|---|---|
| 浏览/检索档案 | 是 | 是 | 由授权决定 |
| 录入/修改分类和档案 | 否 | 是 | 由授权决定 |
| 提交/撤销本人申请 | 是 | 可代办时另行规定 | 由授权决定 |
| 审批、借出、归还 | 否 | 是 | 由授权决定 |
## V1 不做
多级审批、跨部门调阅、全文检索、硬件标签、消息推送。
```

3. 给每项“是/否”写原因；不确定的规则标 `待确认`，不要猜。

### 15:00–18:00｜画两条状态图

1. 用 draw.io 或纸笔建立申请状态图：`已提交 → 已批准`、`已提交 → 已驳回`、`已提交 → 已撤销`；明确谁能触发。
2. 建借阅状态图：批准后创建借阅记录并进入“借阅中”；应还日过去且未还为“逾期”；归还后“已归还”。
3. 在图旁写非法示例：已撤销申请不可审批；已归还不可再次归还；借阅中档案不可删除。

### 19:00–23:00｜权限编码和变更表

1. 建 `permission-matrix.md`，列出最小编码：`archive:category:list/add/edit/remove`、`archive:record:list/add/edit/remove`、`archive:borrow:apply/cancel/approve/reject/lend/return`。
2. 每个操作填三列：操作者、主表、状态变化/副作用。例如 approve：管理员、申请表+借阅记录+档案表、三表事务。
3. 自检：是否有任何按钮没有操作者/权限/数据影响？有则补完。
