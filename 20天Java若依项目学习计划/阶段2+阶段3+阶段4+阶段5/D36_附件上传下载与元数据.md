# D36｜附件上传下载与元数据

> 今日目标：一个档案能拥有多条附件元数据；复用若依既有上传/下载能力，不在前端硬编码服务器文件路径。

## 1. 知识速记

- 文件本体（磁盘/存储）与附件元数据（数据库）不同：元数据记录档案 id、原始名、存储路径、大小、类型、上传时间。
- 一档案对多附件，`archive_attachment.archive_id` 关联档案。
- 上传要校验空文件、大小、允许类型；下载要确保请求者有权访问关联档案。
- 测试只用无敏感、可公开的文本/图片样本。

## 2. 资料

- `CommonController`：在 backend 中搜索类名，定位现有 upload/download 接口和文件配置。
- [若依 Vue：文件上传](https://doc.ruoyi.vip/ruoyi-vue/document/htsc.html)（从官方文档目录进入上传章节）。

## 3. 知识详解

上传成功返回的 URL/路径不应直接等价“任何人可下载”；业务模块要保存它与档案的关联，并在下载前做权限判断。附件表 CRUD 可以由生成器生成，但“先上传文件再保存元数据”“删除记录是否删物理文件”属于业务规则，先写明再让 AI 生成。

## 4. 今天照做

### 09:00–12:00｜读现有能力并设计流程

1. IDEA 搜索 `CommonController`、`upload`、`download`，只读方法映射、参数、返回对象和配置来源。
2. 在 `docs\design\attachment-flow.md` 画：选择文件→现有上传接口→返回路径→提交附件元数据→关联档案→有权限后下载。
3. 核对 D33 `archive_attachment` 字段，补充 `file_name/file_path/file_size/file_type` 注释；不要把文件二进制直接存成普通 VARCHAR。

### 15:00–18:00｜生成元数据模块并接最小流程

1. 用生成器预览 `archive_attachment` CRUD，确认 `archive_id` 不应被任意用户随意改成其他档案。
2. 让 AI 先输出“上传成功后的元数据保存接口、权限校验点、失败场景、需修改文件”；审查后生成最小变更。
3. 前端在档案详情/编辑上下文中调用现有上传能力，上传成功后将返回路径与档案 id 传给附件元数据接口。不要新增另一个文件存储框架。

### 19:00–23:00｜四类测试

1. 创建一条虚构档案，上传两个无敏感测试文件；确认附件表两行记录、路径不为空。
2. 点击下载，确认文件内容/名称正确；Network 记录请求。
3. 测试空附件（不选择文件）和不允许的类型/超限文件，记录项目实际提示；不要上传可执行或敏感文件。
4. 用无权限账号只测试正常 UI/接口拒绝路径，避免绕过授权。截图数据库元数据、成功下载、失败提示。

## 5. AI Agent 操作卡

提供附件表字段、现有上传接口签名、权限规则，要求 AI 给流程和测试清单。严禁给 AI 真附件、存储密钥、服务器真实目录；审核 diff 时重点看路径信任与权限检查。

## 6. 验收与文末答案

- [ ] 一个档案有至少两条附件元数据。
- [ ] 上传/下载都经现有若依能力，前端不硬编码路径。
- [ ] 完成成功、空文件、类型/大小、越权至少四类检查。

答案：附件表为何不直接存文件内容？V1 用存储路径/元数据更适合文件管理；数据库表用于可查询、关联、审计的描述信息。
