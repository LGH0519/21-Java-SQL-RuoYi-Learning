# D37｜借阅申请与撤销

> 今日目标：先有接口草案和状态规则，再由生成器/AI 完成基础申请模块；普通员工只能提交、查看、撤销自己的待审批申请。

## 1. 知识速记

- 申请状态：`已提交`、`已批准`、`已驳回`、`已撤销`；撤销仅允许申请人本人对已提交申请执行。
- 申请前必须检查档案存在且可借阅；不能把前端传来的 applicant_id 当作可信身份。
- 当前登录用户应由若依安全上下文获取，Service 负责所有权和状态判断。

## 2. 资料

- D23 Token/当前用户链路，D32 状态图，D33 申请表字典。
- 若依代码中搜索 `SecurityUtils.getUserId` 或项目实际获取当前用户的方法。

## 3. 知识详解

“撤销自己的申请”包含两道规则：申请记录的 `applicant_id` 必须等于当前登录用户 id，且状态必须为已提交。只在前端过滤列表不安全；直接请求接口仍必须被 Service 拒绝。重复申请规则可设为“同一档案、同一申请人、存在已提交/已批准申请时拒绝”，以 D32 书面规则为准。

## 4. 今天照做

### 09:00–12:00｜接口与状态草案

1. 在 `docs\design\borrow-api-draft.md` 写：提交、查询本人、撤销；每项含 URL 草案、方法、权限、请求字段、响应、状态前置条件、改表。
2. 写状态转换表：提交 `无→已提交`；撤销 `已提交→已撤销`；任何其他起点拒绝。
3. 让 AI 只审查所有权、状态、重复申请遗漏，不生成代码。

### 15:00–18:00｜生成 CRUD 与最小业务规则

1. 在生成器导入 `archive_borrow_application`，先预览字段；申请人 id、审批人 id 等敏感字段不要作为普通员工任意填写的表单输入。
2. 集成基础 CRUD 后，让 AI 分两次生成最小 Service：提交校验、撤销校验。每次先给伪代码/文件清单，再确认 diff。
3. 为提交/撤销操作分别设置后端 `@PreAuthorize` 与前端权限；实际字符串以 D32 矩阵为准。

### 19:00–23:00｜Apifox 状态测试

1. 测试正常提交：用普通员工身份创建申请，DBeaver 看 applicant_id 是当前用户。
2. 重复提交同档案，预期拒绝；测试成功后保留一条待审批申请。
3. 测试本人撤销待审批申请，预期成功；再撤销一次、撤销他人申请/非待审批申请，预期拒绝。
4. 每个失败都记录 Response、Service 断点状态、数据库前后值。

## 5. AI Agent 操作卡

提示 AI 必须先说明“当前用户从哪里来、不可相信哪个前端字段、每个状态的允许/拒绝分支”。若它建议由前端传 applicant_id 并直接保存，拒绝该方案。

## 6. 验收与文末答案

- [ ] 有接口草案、状态表和 AI 审查记录。
- [ ] 普通员工可提交/撤销自己的待审批申请。
- [ ] 重复、非本人、非法状态均被后端拒绝。

答案：为何 applicant_id 不能信任前端？请求可被修改；真实身份必须从已认证的当前用户取得。
