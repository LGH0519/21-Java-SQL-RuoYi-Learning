工程级代码深度解析与二次开发指南指令  
请对指定的工程进行完整、详尽、通俗易懂的解析，并重点输出一份面向“二次开发快速上手”的结构化指南文档。如果在解析过程中发现信息不足或有歧义，请随时向我提问。  
解析对象  
类型：整个工程  
路径：backend/  
语言/格式：自动识别  
输出要求  
请严格按照以下五个维度组织内容，确保逻辑清晰、层次分明：  
   
维度一：前置知识术语表  
在文档开头提供一份术语表，列出贯穿全文的所有关键技术概念。  
格式要求：术语名称 → 英文全称（如有）→ 通俗解释 → 生活类比（以表格形式呈现）。  
目标：确保完全没有该技术栈背景的人，也能通过这张表建立基本认知。  
   
维度二：专有名词通俗化  
对文档中出现的所有专业术语和技术名词：  
在首次出现时必须给出通俗解释，绝对不要假设读者已经知道。  
必须使用生活中的类比（如“管家”、“快递”、“积木”、“超市”、“公司部门”等日常事物）来辅助理解。  
同一个名词在不同上下文中含义不同时，需结合上下文分别解释。  
示例风格：  
Artifact（制品）：项目经过编译打包后最终生成的文件。类比：你做了一个蛋糕，蛋糕就是 artifact。面粉鸡蛋是依赖，烤箱是插件，做蛋糕的过程是构建。  
   
维度三：整体架构与关系图解  
使用 Mermaid 语法绘制模块/文件之间的依赖关系图、调用关系图或层次结构图。  
对图中的每个节点和箭头给出通俗解释，说明各模块/文件是如何像积木一样拼装协作的。  
说明整个工程的构建顺序或启动流程。  
用生活化类比总结整体架构（例如：“整个工程就像一家公司的组织架构，A模块是前台，B模块是安保部……”）。  
   
维度四：核心文件/模块深度剖析  
挑选工程中最核心、最具代表性的文件和模块进行详细解释：  
角色定位：它在整个工程中扮演什么角色？  
核心逻辑：它内部的关键代码段/配置项是如何工作的？  
应用场景：在实际开发中，这个部分对应什么具体的业务场景？  
修改影响：如果修改了这里的配置或代码，会对系统的其他部分产生什么连锁反应？  
   
维度五：二次开发快速上手指南（ 本次核心重点）  
本维度是本次解析的重中之重，请提供极具实操性的指南，帮助我快速具备独立进行二次开发的能力。必须包含以下四个子模块：  
核心目录/文件速查字典  
列出后续开发中最常需要修改的文件夹和核心文件。  
提供“场景化寻址指南”（例如：“如果要修改登录逻辑，去改 XX 文件”、“如果要调整数据库连接，去改 XX 文件”）。  
典型业务链路追踪  
选取一个核心功能（如“用户登录”或“列表分页查询”），完整梳理其数据流转过程。  
链路需涵盖：前端请求发起 -> 路由/拦截器 -> Controller -> Service -> Mapper/DAO -> 数据库，并说明每一层的具体职责。  
新增业务模块标准 SOP（标准作业程序）  
假设我需要新增一个全新的业务模块（例如“档案管理”），请给出从 0 到 1 的标准开发步骤。  
步骤需包含：数据库表设计 -> 后端实体类/DTO/VO -> Mapper层 -> Service层 -> Controller层 -> 前端页面（Vue/JS）的具体操作顺序、命名规范及注意事项。  
核心机制与避坑指南  
指出本工程中特有的自定义机制（如：自定义数据权限注解、全局异常处理、操作日志AOP、防重复提交等），并说明如何在二次开发中复用它们。  
列出在该工程中进行二次开发时，极易踩坑的注意事项（如：缓存一致性、事务失效场景、权限拦截绕过等）。  
   
语言与排版风格要求  
受众定位：面向非计算机专业人员或刚接手该项目的新人，必须通俗易懂。  
类比优先：每个抽象概念首次出现时，必须用生活化类比解释。  
禁忌词汇：严禁使用“显然”、“很容易理解”、“不言而喻”、“众所周知”等假设读者已知的表述。宁可多说一句，也不要省略关键解释。  
排版规范：使用清晰的 Markdown 标题层级（H2/H3/H4）、加粗、列表和代码块，确保长文档的阅读体验良好。
