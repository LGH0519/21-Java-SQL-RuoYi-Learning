## 完整的传递链路

```
① throw new ServiceException("获取用户ID异常", 401)
   ↓
② 异常沿着调用栈往上抛
   ↓
③ Spring 的 DispatcherServlet 捕获异常
   ↓
④ 交给 GlobalExceptionHandler 处理
   ↓
⑤ 封装成 AjaxResult 返回给前端
```

## 逐步详解

### ① 你的代码抛出异常

```java
// SecurityUtils.java
throw new ServiceException("获取用户ID异常", HttpStatus.UNAUTHORIZED);
```

### ② 异常沿调用栈往上抛

```
正常调用栈（从下往上）、异常调用（从上往下）：
    SecurityUtils.getUserId()         ← 异常在这里产生
    ↑
    SysLoginService.login()           ← 没有 try-catch，继续往上抛
    ↑
    SysLoginController.login()        ← 没有 try-catch，继续往上抛
    ↑
    DispatcherServlet                 ← Spring 的"总调度器"，在这里被拦截！
```

> 异常就像"烫手山芋"——每一层方法都没有接住（没有 try-catch），就一直往上抛，直到有人接住为止。

### ③ Spring 的 DispatcherServlet 捕获

`DispatcherServlet` 是 Spring MVC 的**总调度器**，所有请求都经过它。当它发现 Controller 方法抛了异常，不会让异常继续往上抛，而是交给**全局异常处理器**处理。

DispatcherServlet 本身并不"理解"业务异常，它只是一个通用的异常捕获者——用 try-catch 把 Controller 执行过程中抛出的所有异常兜住，然后交给 HandlerExceptionResolver 链去处理。若依的 GlobalExceptionHandler 就是这条链上的关键一环，负责把异常转成统一的 AjaxResult 格式返回。

```
DispatcherServlet 捕获异常
       ↓
HandlerExceptionResolver 链（有多个实现类）
       ↓
ExceptionHandlerExceptionResolver  ← 这个才是关键！
       ↓
扫描 @RestControllerAdvice 标注的类
       ↓
找到 GlobalExceptionHandler 中匹配的 @ExceptionHandler 方法
```

### ④ GlobalExceptionHandler 处理

```java
// GlobalExceptionHandler.java（第 58-64 行）
@ExceptionHandler(ServiceException.class)
public AjaxResult handleServiceException(ServiceException e, HttpServletRequest request)
{
    log.error(e.getMessage(), e);                    // 记录日志
    Integer code = e.getCode();                       // 取出错误码 401
    return StringUtils.isNotNull(code) 
        ? AjaxResult.error(code, e.getMessage())      // 封装成 { code: 401, msg: "获取用户ID异常" }
        : AjaxResult.error(e.getMessage());
}
```

### ⑤ 返回给前端

前端收到的 JSON：

```json
{
    "code": 401,
    "msg": "获取用户ID异常"
}
```

前端根据 `code` 判断：401 → 跳转登录页。

## 关键机制：`@RestControllerAdvice` + `@ExceptionHandler`

```java
@RestControllerAdvice                  // ← 告诉 Spring："我是全局异常处理器"
public class GlobalExceptionHandler
{
    @ExceptionHandler(ServiceException.class)  // ← 告诉 Spring："专门处理 ServiceException"
    public AjaxResult handleServiceException(ServiceException e, HttpServletRequest request)
    {
        // 处理逻辑
    }
}
```

| 注解                             | 作用                                  | 类比                 |
| ------------------------------ | ----------------------------------- | ------------------ |
| `@RestControllerAdvice`        | 标记这是一个全局异常处理器，监听所有 Controller 抛出的异常 | "总客服"——所有客户的投诉都转给我 |
| `@ExceptionHandler(Xxx.class)` | 指定处理哪种异常                            | "我专门处理退货类投诉"       |

## 为什么不是定时器？

| 方式 | 机制 | 响应速度 | 本项目用的是？ |
|------|------|---------|-------------|
| **定时器扫描** | 每隔一段时间检查有没有异常 | 慢（可能延迟几秒） | ❌ 不是 |
| **事件驱动** | 异常一抛出，立刻被拦截处理 | 快（毫秒级） | ✅ 是 |

> 类比：定时器像"保安每 10 分钟巡逻一次"——小偷进来后要等 10 分钟才被发现。事件驱动像"门口装了报警器"——小偷一进门，警报立刻响，保安立刻处理。

## DispatcherServlet 的作用有哪些？

用一个生活化的类比：**DispatcherServlet 就像酒店的"前台总机"**。所有客人（HTTP 请求）打进电话，都先到总机，总机负责问清楚你要找谁，然后帮你转接到对应的房间（Controller 方法）。

它的核心职责可以归纳为 **5 件事**：

### ① 请求路由（找 Controller）
根据请求的 URL，通过 `HandlerMapping` 找到对应的 Controller 方法。
> 比如 `GET /system/user/list` → 找到 `SysUserController.list()`

### ② 参数解析与绑定
把 HTTP 请求中的参数（URL 参数、JSON body、路径变量等）解析并绑定到 Controller 方法的参数上。
> 比如 `@RequestBody SysUser user` → 把 JSON 转成 Java 对象

### ③ 调用 Controller 方法
通过 `HandlerAdapter` 执行找到的 Controller 方法，拿到返回值。

### ④ 返回值处理
把 Controller 的返回值（`AjaxResult`、`ModelAndView` 等）转换成 HTTP 响应（JSON、HTML 等）。
> 比如 `AjaxResult` → 序列化成 JSON 写入 response

### ⑤ 异常兜底捕获
如果上面任何一步抛了异常，`DispatcherServlet` 用 `try-catch` 兜住，然后交给异常处理链（`HandlerExceptionResolver`）处理。
> 这就是你图片中第 ③ 步 → 第  步的过程

## 上端下发的信息都经过它吗？

**几乎所有经过 Spring MVC 的请求都会经过它**，但有例外：

```
前端请求
  │
  ▼
┌─────────────────────────────────────────┐
│  Servlet 容器 (Tomcat)                    │
│  ┌───────────────────────────────────┐  │
│  │  Filter 链 (XssFilter, RepeatableFilter等) │  ← ① 先经过 Filter
│  └───────────────────────────────────┘  │
│              │                           │
│              ▼                           │
│  ┌───────────────────────────────────┐  │
│  │  DispatcherServlet                │  │  ← ② 再经过它
│  │  (URL 匹配 / 或 /api/*)            │  │
│  ───────────────────────────────────┘  │
│              │                           │
│              ▼                           │
│  Controller → Service → DAO              │
└─────────────────────────────────────────
```

### 会经过 DispatcherServlet 的请求：
- 所有 URL 匹配 `DispatcherServlet` 映射路径的请求（若依中通常是 `/`，即**所有请求**）
- 包括登录、查询、上传文件、下载文件等所有业务接口

### 不会经过 DispatcherServlet 的请求：
| 情况 | 说明 |
|------|------|
| **静态资源**（如果被配置绕过） | 比如 `ResourcesConfig` 中配置的静态文件路径，可能直接由容器处理 |
| **Filter 中直接返回的响应** | 比如 `XssFilter` 如果直接 reject 了请求，就不会到 DispatcherServlet |
| **其他 Servlet** | 如果项目中注册了别的 Servlet（非 DispatcherServlet），走那条路的请求不经过它 |

## 结合 GlobalExceptionHandler 看完整链路

```
前端发请求 → Filter链 → DispatcherServlet.doDispatch()
                                    │
                          ┌─────────┴──────────┐
                          │  try {               │
                          │    找Controller       │
                          │    执行Controller     │  ← 这里抛了 ServiceException
                          │  } catch (Exception) {│
                          │    dispatchException = ex  ← ③ 捕获
                          │  }                    │
                          └─────────┬──────────┘
                                    │
                          processDispatchResult()
                                    │
                          HandlerExceptionResolver 链
                                    │
                          ┌─────────▼──────────┐
                          │ GlobalExceptionHandler │  ← ④ 处理
                          │ @ExceptionHandler      │
                          │ (ServiceException.class)│
                          │ → return AjaxResult    │
                          └─────────┬──────────┘
                                    │
                          ⑤ AjaxResult JSON → 前端
```

**一句话总结**：`DispatcherServlet` 是 Spring MVC 的**中央调度器**，几乎所有业务请求都经过它。它本身不写业务逻辑，只负责"分发 + 兜底"——把请求分给对应的 Controller，如果出错了就兜住交给 `GlobalExceptionHandler` 统一处理。
